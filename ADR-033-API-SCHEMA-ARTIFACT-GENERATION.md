## Problem

`05_API_CAPABILITY_CONTRACTS.md` requires two things that do not exist yet:

- §1 — "OpenAPI and JSON Schema artifacts are **generated from code** and committed. A hand-written schema that drifts from the handler is a defect."
- §8 — "Generated schema artifacts are committed on every contract change, and **a CI check fails when generated output differs from the committed artifact**."

The `store.read` golden path ships with neither. With one capability the gap is trivial; Task 2 adds seven more, so the cost of deciding this late rises with every slice. Flagged as MISSING in `PHASE_1_REVIEW_AUDIT.md` §3.3.

## Constraint that eliminates the obvious choice

The conventional answer for a NestJS codebase is `@nestjs/swagger` with its CLI plugin, which infers request/response schemas from TypeScript types. **That inference cannot work in this repository.** As established while building the golden path (`DECISION_LOG.md`, "NestJS's type-based constructor DI silently fails under esbuild/tsx"), everything here runs through `tsx`/Vitest, both esbuild-based, and **esbuild does not implement `emitDecoratorMetadata`**. `@nestjs/swagger`'s type inference reads exactly that metadata. It fails silently — producing an empty or wrong schema rather than an error — which is the worst possible failure mode for an artifact whose entire purpose is to not drift.

`@nestjs/swagger` can still be driven manually with explicit `@ApiProperty()` decorators on every field. That is a hand-maintained description of the shape, sitting next to a separate Zod schema that actually validates it — two sources of truth for one contract, free to diverge. §1 forbids precisely this.

## Decision

1. **Zod is the single source of truth for every capability's input and output shape.** `application/<use-case>.input.ts` already holds the input schema (`readStoreInputSchema`). Output schemas join it in the same file. Nothing describes a shape twice.

2. **OpenAPI is generated from those Zod schemas**, via `@asteasolutions/zod-to-openapi` (or an equivalent that reads Zod directly). No decorator-based schema description is added anywhere, and the `@nestjs/swagger` CLI plugin is not enabled.

3. **Capability metadata comes from the `CapabilityDefinition`**, not from decorators — `id`, `version`, `requiredPermissions`, `risk`, `idempotent`, `storeScoped` are already declared in `interfaces/<capability>.capability.ts` and are the natural source for operation ids, security requirements and documentation.

4. **The artifact is generated by a script and committed**: `npm run openapi:generate` writes `contracts/openapi.json` (path to be fixed on acceptance). It is a build output that lives in version control, like a lockfile.

5. **CI fails on drift.** A `npm run openapi:check` step regenerates into a temp location and diffs against the committed artifact, failing when they differ, satisfying §8. This runs in the existing conformance workflow rather than a new one.

6. **Every documented error code a capability can raise appears in its OpenAPI responses**, sourced from the shared taxonomy in `modules/capability/domain/capability.errors.ts`, so the published contract and the enforced contract cannot disagree.

## Alternatives rejected

| Option | Why not |
|---|---|
| `@nestjs/swagger` + CLI plugin type inference | Silently broken under esbuild — see the constraint above |
| `@nestjs/swagger` + explicit `@ApiProperty()` | Two sources of truth per contract; §1 calls the drift this permits a defect |
| `nestjs-zod` | Viable and closer to Nest idiom, but couples artifact generation to the HTTP framework. Capabilities are reachable from MCP/AI/automation too (`05` §1, "REST, Admin UI, Storefront, AI, MCP … converge on the same Application Service"), so generation should key off the capability + Zod schema, not the controller |
| Hand-written OpenAPI | Explicitly forbidden by `05` §1 |

## Consequences

- Adding a capability without an output schema becomes a visible omission in the generated artifact rather than an invisible one.
- The generator must run in CI on a machine with no database, so it must not import anything that opens a connection at module load. Note that `store.controller.ts` currently calls `createDb()` at module scope — that pattern needs revisiting when the generator is built, or generation must key off capability definitions and schemas only, never the controller module.
- Response-shape changes become reviewable as artifact diffs in the pull request.

## Verification

- [ ] `npm run openapi:generate` produces a committed artifact covering every implemented capability
- [ ] the CI drift check fails on an intentionally stale artifact (deliberately failing fixture, per ADR-030's own standard)
- [ ] no `@ApiProperty` decorator and no hand-written schema exists anywhere in the repository
- [ ] the generator runs with no database reachable
- [ ] every error code a capability can raise appears in its documented responses
