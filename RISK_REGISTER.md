| R-002 | A table's owning PostgreSQL role bypasses `ENABLE ROW LEVEL SECURITY` entirely by default (confirmed empirically). This Phase 0 scaffold originally used one role for both migrations and app queries, which would have silently violated `08_PHASE_1_BRIEF.md` §5 ("the application database role cannot bypass RLS") the moment real tenant-owned tables existed. | N/A — closed before any real migration existed | Would have been critical — silent cross-tenant data exposure, and every tenant-isolation test would have passed for the wrong reason | Three independent layers, all implemented and verified 2026-08-22, see `DECISION_LOG.md` "RLS: FORCE ROW LEVEL SECURITY or a non-owner app role": (1) role separation — `nexora_migrate` owns/migrates, `nexora_app` (NOSUPERUSER, NOBYPASSRLS, never an owner) is the only role the app/tests use; (2) `FORCE ROW LEVEL SECURITY` on every tenant-owned table, now a mechanical conformance rule (`SCHEMA-MISSING-FORCE-RLS`) in both the static and live-DB schema checkers; (3) a runtime assertion (`platform/db/assert-role-safety.ts`) that fails fast if the connected role could bypass RLS, wired into `platform/db/tenant-context.spec.ts`, and confirmed to actually fire against both a superuser and an owner-role misconfiguration. | AI implementer | RESOLVED | 2026-08-22 |
