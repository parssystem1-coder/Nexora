| R-003 | Tenant isolation for the two membership tables depends on an RLS clause keyed on `app.user_id`, not on `tenant_id` alone: `USING (tenant_id::text = current_setting('app.tenant_id', true) OR user_id::text = current_setting('app.user_id', true))`. It exists because pipeline steps 2–3 must read these tables *before* step 5 establishes tenant context (`08_PHASE_1_BRIEF.md` §2), so a `tenant_id`-only policy returns zero rows and no request can ever resolve store access. The clause therefore widens the policy beyond what §5 describes, and any bug in how `app.user_id` is set would widen it further. **Location (the instruction referenced `modules/tenant/infrastructure/store-memberships.rls.sql`, which does not exist — RLS lives in the creating migration per §5's "in the same migration" rule):** `modules/tenant/migrations/20260822090300_tenant__create_memberships.sql` and `20260822090500_tenant__create_store_memberships.sql`. `app.user_id` is set in exactly one place, `platform/db/tenant-context.ts`. | Low — the clause is narrow, applies to two tables only, and `app.user_id` is set by the single `@singleton-role: tenant-context` helper that `DB-ACCESS-TRANSACTION-BYPASSES-HELPER` forbids bypassing | High if wrong — it is the gate in front of the store access check, so a defect here is a cross-tenant read | Kept deliberately (`DECISION_LOG.md`, decided 2026-08-22): removing it disables the system rather than hardening it. Must not be copied to other tenant-owned tables without its own decision. Covered by tests asserting cross-tenant denial and RLS-fails-closed. **Task 2 re-evaluates a clause-free alternative** — a `SECURITY DEFINER` bootstrap function, or an authoritative tenant on the session row so `app.tenant_id` is known from step 1 and the bootstrap phase disappears (this couples to the `sessions` decision). **Update 2026-08-23 (`organization.create`, Task 2 slice 1 — documentation only; no policy changed and no migration in that commit):** the first code to *write* a `memberships` row does not need this clause. `organization.create` inserts the creator's membership inside a transaction where `app.tenant_id` is already the new organization's id, so the `tenant_id` half of the policy satisfies the insert on its own — `memberships` declares only `USING` with no `WITH CHECK`, so Postgres reuses the `USING` expression as the insert check. The clause's justification therefore narrows to one caller: `StoreAccessGuard`'s bootstrap *read*. That does not weaken the "removing it disables the system" finding, which was always about that read. **Realistic forcing point: slice 5 (`auth.login`).** Slices 2 and 3 (`membership.invite`, `membership.role.assign`) both run inside an already-established tenant context and never touch the bootstrap read, so neither will force a decision on its own. Of the two alternatives above, the session-row one couples directly to the `sessions`/`credentials` tenancy decision that slice 5 has to take anyway; the `SECURITY DEFINER` one is not coupled to it, but nothing before slice 6 forces it either. Resolving this at slice 5 should therefore be a deliberate choice rather than something discovered at the end of Task 2. **Update 2026-08-23 (`auth.login`, Task 2 slice 5 — the forcing point, evaluated deliberately, no policy changed): both alternatives evaluated on their merits and rejected.** (i) A `SECURITY DEFINER` bootstrap function remains uncoupled to the `credentials` tenancy decision this slice actually made (`credentials` joined the identity exemption, same as `sessions` — see `DECISION_LOG.md`) — nothing here forces building it, and it would trade the current narrow, already-tested RLS surface for a new privileged-function trust boundary with no offsetting need. (ii) "An authoritative tenant on the session row," the alternative this row named as coupled to slice 5, is not actually available even now that `sessions` exists in its final Phase-1 shape: `active_organization_id` is present, but ADR-002 and ADR-029 item 5 are explicit it is session state, a UI convenience, never authority for tenant resolution — trusting it as authoritative would mean either accepting a staleness window after a membership is revoked (a real regression against ADR-029's own "cached membership invalidates on membership change" verification item) or re-querying `memberships` to confirm it, which is the identical bootstrap read this clause already exists to permit, merely relocated. Neither alternative removes the need for the clause. | User + AI implementer | ACCEPTED — clause kept permanently by evaluated decision; both alternatives evaluated and rejected on their merits, not deferred further. **Corrected 2026-08-24** (was `RESOLVED`): the underlying risk — a policy wider than `tenant_id` alone — is retained by design, not eliminated; `RESOLVED` reads as "gone" to a future phase-gate review, which this is not. | 2026-08-22 |
| R-002 | A table's owning PostgreSQL role bypasses `ENABLE ROW LEVEL SECURITY` entirely by default (confirmed empirically). This Phase 0 scaffold originally used one role for both migrations and app queries, which would have silently violated `08_PHASE_1_BRIEF.md` §5 ("the application database role cannot bypass RLS") the moment real tenant-owned tables existed. | N/A — closed before any real migration existed | Would have been critical — silent cross-tenant data exposure, and every tenant-isolation test would have passed for the wrong reason | Three independent layers, all implemented and verified 2026-08-22, see `DECISION_LOG.md` "RLS: FORCE ROW LEVEL SECURITY or a non-owner app role": (1) role separation — `nexora_migrate` owns/migrates, `nexora_app` (NOSUPERUSER, NOBYPASSRLS, never an owner) is the only role the app/tests use; (2) `FORCE ROW LEVEL SECURITY` on every tenant-owned table, now a mechanical conformance rule (`SCHEMA-MISSING-FORCE-RLS`) in both the static and live-DB schema checkers; (3) a runtime assertion (`platform/db/assert-role-safety.ts`) that fails fast if the connected role could bypass RLS, wired into `platform/db/tenant-context.spec.ts`, and confirmed to actually fire against both a superuser and an owner-role misconfiguration. | AI implementer | RESOLVED | 2026-08-22 |
| R-004 | Store slug uniqueness (`04_DATABASE_BLUEPRINT.md` §5) is enforced per-organization — `UNIQUE (tenant_id, slug)` on `stores`, added in Task 1 and unchanged by `store.create` (Task 2 slice 4). Two different organizations can each hold a store slugged `shop` today — proven directly by `apps/api/store-create.integration.spec.ts`'s "the SAME slug succeeds in a DIFFERENT organization" test, which is asserting the *current, correct-per-04-§5* behavior, not a bug. | Low today — no subdomain routing exists yet, so the collision has no runtime consequence in Phase 1 | High at Phase 4 — ADR-028 requires deterministic host resolution (`UNIQUE (hostname_ascii) WHERE status = 'VERIFIED'`, platform-global) for *verified custom domains*; nothing in the docs pack states whether platform-provided subdomains (`{slug}.<platform-domain>`) are governed by that same rule or need their own. If they do, per-organization slug uniqueness and platform-global subdomain uniqueness are in direct tension, and two stores that validly share a slug today cannot both keep a `{slug}.<platform-domain>` address once one is assigned. | Not solved here, deliberately (`DECISION_LOG.md`, 2026-08-23, `store.create` decision 6) — ADR-028/ADR-019 host resolution is Phase 4, and `AGENTS.md` §4 forbids building for `future/`.
