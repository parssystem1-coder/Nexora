## 2026-08-24 — CI never ran migrations: the workflow was not actually equivalent to the local gate

**Context:** the first real push to `origin/main` (this repository had no history on the remote before 2026-08-23) triggered `.github/workflows/conformance.yml` for the first time ever. It failed: 11 of 29 test files failed, every failure being `relation "users" does not exist` or `relation "audit_events" does not exist`. Reading the workflow confirmed the cause directly — it goes `checkout → setup-node → npm ci → start Postgres (docker compose) → typecheck → npm test → npm run conformance → graph --check → openapi --check`, with no migration step anywhere. `CLAUDE.md`'s stated local verification ritual is `npm run typecheck && npm test && npm run conformance && npm run db:migrate` — four gates. The workflow only ever implemented three; the fourth was never run anywhere, on any machine, against the compose database. CI was never actually equivalent to what the local ritual claims to guarantee, which is exactly the gap `06_IMPLEMENTATION_PLAN.md`'s "a phase exit is a test in CI, never a screenshot" exists to prevent.

**Decision 1 — where the migration step goes.** Immediately after "Start PostgreSQL", before "Type check". `npm test` strictly requires the migrated schema, so it must run after migrations regardless. Type check does not touch the database at all, so its position relative to the migration step is functionally inert — but placing migrations first groups the two environment-provisioning steps (start the container, then give it a schema) together as one completed phase before any verification step runs, and means a broken migration fails fast with an unambiguous signal rather than being buried after an unrelated (and passing) type-check step.

**Decision 2 — this step does double duty, and says so in a comment.** The compose container starts with an empty volume on every run, by construction. Running `npm run db:migrate` against it is therefore not just "give the tests a schema" — it is exactly the "every migration applies cleanly from an empty database" proof that had only ever been done by hand on this machine, against a throwaway database created and dropped around each slice's verification pass. That property now holds automatically, on every push, without anyone remembering to check it. Recorded as a comment in the workflow itself, not only here, since it is a property of what CI now guarantees, not a one-off implementation note.

**Decision 3 — `if: always()` added to the three post-test checks (`conformance`, `graph -- --check`, `openapi -- --check`), not to `npm test` or `Type check`.** These three checks are functionally independent of `npm test`'s outcome: `graph`/`openapi` are pure static generation checks with no database dependency at all, and `npm run conformance`'s live-DB schema checker only needs the schema the migration step already applied earlier and independently — it does not depend on any table state a failing *test* might have left behind, since tests run in the same migrated-but-otherwise-fixed schema regardless of which assertions inside them pass or fail. Without `if: always()`, a single unrelated test regression hides three independent signals behind "skipped," meaning a maintainer fixing that one regression could still be surprised by a conformance or drift failure on the *next* push instead of learning about it immediately. The tradeoff this weighs against — noise from running checks after a "broken build" — does not really apply here, because these three checks cannot produce spurious noise from `npm test` failing: they do not read `npm test`'s output or any state it produces. `continue-on-error` was deliberately NOT added to anything: these three still fail the job when they fail, `if: always()` only controls whether they *run* when an earlier step already failed, not whether their own failure is tolerated.

**Verified locally before pushing, unchanged from the last known-good numbers** (this commit touches only `.github/workflows/conformance.yml` plus `RISK_REGISTER.md`): typecheck clean, 288 tests passing across 29 files, conformance 0 violations with an empty exceptions report, 19 migrations already applied against the live database (0 newly applied, confirming nothing about the schema itself changed).

**RISK_REGISTER.md R-001 updated, not closed outright:** the first real CI run proved three previously-unverified things favorably (compose Postgres starts and is reachable on port 5433; `npm ci` resolves `@node-rs/argon2`'s Linux prebuilt binary; TypeScript compiles cleanly on `ubuntu-latest`/Node 24) despite the run itself being red for the migration-step reason above. Status changed to `PARTIALLY CLOSED` — a fully green run, including the live-DB conformance scan and the `graph`/`openapi` drift checks on Linux (neither ever executed there before), is still needed before this row closes outright.

**Status:** RESOLVED for the workflow fix. R-001 remains open in its narrowed form until a fully green run is observed.

## 2026-08-24 — `auth.logout` / `auth.logout_all`: one slice, eight decisions, plus three corrections from review

**Context:** implementing Task 2 slice 5's remaining two capabilities (`08_PHASE_1_BRIEF.md` §3). Both share `auth.login`'s divergence from the golden path (no tenant, no organization, no transaction) but add a guard (`SessionGuard`) that `auth.login` structurally cannot have, plus a new question neither of the first two slice-5 capabilities raised: how far does "logout" reach, and what happens to the session doing the asking.

**Why one slice, not two, despite the `/new-slice` skill's "one slice per invocation" rule.** `auth.logout` and `auth.logout_all` are a single numbered item in `08_PHASE_1_BRIEF.md` §3 (`5. auth.login, auth.logout, auth.logout_all`), share one application-layer concern (ending sessions), one new port (`SessionTerminationRepository`, decision 2), one route prefix (`/api/v1/auth`), one audit shape (ADR-035's sentinel, both under `resource_type` values decided together in decision 7), and — most concretely — the two capabilities are what make each other's tests meaningful: proving "`auth.logout` does NOT end the user's other sessions" and "`auth.logout_all` ends EVERY session, including the caller's own" is the same two-session fixture read two different ways, and splitting them into separate runs would mean writing that fixture twice or leaving one capability's isolation property unproven until the other existed. Building them apart would also have forced an intermediate state where `SessionTerminationRepository` had only one of its two methods, reviewed once and then reopened — churn the rule exists to prevent, not honor literally here.

**1. Routes and response shape.** `POST /api/v1/auth/logout` and `POST /api/v1/auth/logout-all` — the capability id's underscore (`auth.logout_all`) becomes a hyphen in the URL, consistent with this codebase's other kebab-case route segments (e.g. `membership-role`). Both return `200` with a JSON body rather than `204 No Content`: `CapabilityDefinition.outputSchema` is a required `ZodTypeAny` with no special-cased "no body" variant, and the ADR-033 OpenAPI generator's response-building code has no 204 branch — inventing one for two routes that have something worth saying anyway (`auth.logout_all`'s count) would be new machinery for no real need. `auth.logout` returns `{}` (nothing more to report than "it happened"); `auth.logout_all` returns `{ sessionsRevoked: number }`, the one fact its broader effect makes available that "it happened" alone does not.

**2. Extending the revocation port — as a new sibling interface, not a widened `SessionRevocationRepository`.** The instruction driving this slice was to extend `SessionRevocationRepository` rather than open a second raw-SQL path into `sessions`, while keeping `revokeAllForUser` — and its one caller's hand-written fake, `assign-membership-role.service.spec.ts` — working untouched. Those two goals conflict under TypeScript's structural typing: adding a new *required* method to `SessionRevocationRepository` would force that fake (typed exactly as `SessionRevocationRepository`, no more) to implement it too, which is precisely what "untouched" ruled out. **Decision:** a second interface, `SessionTerminationRepository` (`revokeOne(sessionId, userId, revokedAt)`, `revokeAll(userId, revokedAt): Promise<number>`), declared in the same file (`session-revocation.repository.ts`) and implemented by the same `SessionRevocationRepositoryPg` class — one adapter, one place that ever writes a revocation to `sessions`, just reached through two narrow ports instead of one growing one. `revokeAllForUser`'s signature, body, and every existing caller and test are byte-for-byte unchanged; confirmed by running `assign-membership-role.service.spec.ts` with zero edits. `revokeAll` returns a count (via `executeTakeFirst().numUpdatedRows`) precisely because `revokeAllForUser` could not, without changing a return type its one caller's fake could not absorb.

**3. `auth.logout_all` ends the caller's own session too.** Decided by direct precedent, not fresh reasoning: `membership.role.assign` (slice 3) already established that a capability which can affect the caller's own session does not get a special case carved out for that — self-role-assignment revokes the assigner's own session as an "accepted consequence, not a special case." Excluding the caller's session from `auth.logout_all` would mean either passing the caller's `sessionId` through to be excluded (a parameter the port and the underlying `UPDATE ... WHERE user_id = $1 AND status = 'ACTIVE'` don't need for any other reason) or leaving the caller nominally "logged out everywhere except where they're currently logged in" — a confusing half-measure ADR-029 item 6's "logout-all-devices" trigger does not describe. Ending every session, no carve-out, is both the simpler implementation and the more honest one.

**4. A second call to either capability returns `AUTHENTICATION_REQUIRED`, not a repeated 200.** `SessionGuard` runs before the controller and rejects a missing/revoked cookie before the capability's own code ever executes — so a client that calls `auth.logout` (or `auth.logout_all`) twice with the same cookie gets 401 the second time. This is the guard's ordinary behavior, unchanged for this slice, but it was worth deciding deliberately rather than accepting by default: many APIs make logout unconditionally return success. Doing that here would require either running this one route without `SessionGuard` (contradicting the guard-resolves-identity-first shape every other capability in this codebase follows) or auditing an attempt with no resolved actor (conflicting with ADR-034/035, which need a session or user id to attribute the row to). `05` §4.1 already marks `auth.logout` **not** idempotent, which is consistent with — not incidental to — this outcome: a second call is honestly a different situation (no session left to end), not a repeat of the same successful one. No audit event is written for the rejected second call, the same as every other guard-level rejection in this codebase.

**5. Idempotency — stated for both, not inherited as one boilerplate paragraph.** `auth.logout` (`05` §4.1: `LOW_WRITE`/no) carries no divergence, same as `auth.login`. `auth.logout_all` (`MEDIUM_WRITE`/**yes**) is the more interesting case: unlike every earlier capability's ADR-009 divergence note (all of which flagged "marked idempotent in `05` but nothing enforces it, Phase 2"), this one needs **no** divergence flag at all — the underlying operation ("revoke every ACTIVE session for this user") is naturally idempotent regardless of whether an idempotency store exists, because calling it again finds zero ACTIVE sessions left and revokes zero, every time, with no compounding side effect. The one real subtlety (recorded in the capability's own doc comment and proven by an integration test): the *literal same HTTP request* cannot actually be replayed, because the first call revokes the very cookie that would have to authenticate a retry (decision 4) — so "idempotent" here means "a fresh, still-valid session calling this again converges to zero," not "the identical request can be resent."

**6. The cookie is cleared with the same attributes it was set with.** `response.clearCookie("sid", { httpOnly: true, secure: true, sameSite: "lax", path: "/" })` in both controllers, matching `auth.login`'s `response.cookie(...)` call minus `maxAge` (clearing supplies its own expiry). A clearing `Set-Cookie` whose attributes don't match the original is a cookie the browser treats as a *different* one and never actually removes — proven directly in `apps/api/auth-logout.integration.spec.ts` by asserting the cleared cookie's own `Set-Cookie` header carries `HttpOnly`/`Secure`/`SameSite=Lax`/`Path=/`, not asserted only in a comment.

**7. Audit `resource_type`/`resource_id`, and what makes `auth.logout_all`'s row useful.** `auth.logout`: `resource_type: "session"`, `resource_id: <the ended session's id>` — there is exactly one session this action is about, the same shape `auth.login` uses. `auth.logout_all`: `resource_type: "user"`, `resource_id: <the user's id>` — there is no single session id this action is "the" target of, since it acts on the caller's whole session set; naming the user instead of an arbitrary member of that set is the honest description of what was acted on. `auth.logout_all`'s `metadata: { sessionsRevoked }` is what makes that row more useful than a bare outcome: without it, a platform operator reading the audit trail could not tell "ended one stale session" from "ended twelve," and the capability's own effect already computes the number for free.

**8. Pipeline accounting**, written out rather than claimed as a mirror of the golden path or restated from `auth.login`: **Step 1** is `SessionGuard`, unchanged — and here it is also the entirety of what steps 2–4 would otherwise resolve, since there is no organization or store; `request.authenticatedIdentity` already names the exact session (and user) this request acts on, with no further resource id to accept or validate from the client. **Step 5** (transaction): none, same reasoning as `auth.login` — `sessions` is RLS-exempt and each capability's one `UPDATE` is atomic on its own. **Step 6** (permission): none — a user always may end their own session(s); there is no target other than themself to authorize against, so `requiredPermissions: []` for both, the same structural reason `auth.login` and `organization.create` declare it empty. **Step 7** is `LogoutService`/`LogoutAllService`. **Steps 8–10 survive unchanged**: one durable audit event under ADR-035's sentinel — the sentinel's second and third users, the first real evidence it generalizes rather than being built for `auth.login` alone; the stable error envelope; structured logging with `tenantId: null`, honestly.

**Corrections from independent review, folded into this same commit:**

**(a) ADR-035's sentinel safety was an improbability argument, not a guarantee — closed with a `CHECK` constraint.** `PLATFORM_TENANT_ID`'s safety rested on "`gen_random_uuid()` effectively never produces this value" and "no foreign key exists to violate it" — true, but neither actually *forbids* an `organizations` row from holding it, whether by a future manual insert, a seed script, or some later capability that accepts a client-supplied id. Such a row would read every platform-scope audit event ever written. **Decision:** a forward-only migration (`modules/tenant/migrations/20260824090000_tenant__forbid_platform_tenant_id_sentinel.sql`) adds `CHECK (id <> '00000000-0000-0000-0000-000000000000'::uuid)` to `organizations`. A `CHECK` constraint was chosen over a live-DB conformance rule because it prevents the bad row from ever being written, by any future writer, rather than merely detecting it after the fact the next time someone happens to run `npm run conformance` — the same "a rule enforced only by a comment is not enforced" reasoning the role-catalog agreement test already applies elsewhere. Verified directly: an `INSERT` naming the sentinel id now fails with `organizations_id_not_platform_tenant_sentinel`. ADR-035 amended (decision 5) rather than silently reopened — see `02_ADR_INDEX_NORMATIVE_DECISIONS.md`.

**(b) `actor_user_id`'s documented meaning was incomplete, not the stored value.** `20260822090800_audit__create_audit_events.sql`'s own comment says `actor_user_id` "is nullable for non-user actors" — but `auth.login` has written `actor_type = 'user'` with `actor_user_id = NULL` for an unknown-email attempt since its first commit. The **value** is correct: the actor really is a human being attempting to authenticate, not the system acting on its own; reclassifying it as a non-`'user'` `actor_type` to satisfy the old comment would misrepresent who did this to make the comment true instead of the other way around. **Decision:** correct the documented meaning, not the code. Migrations are forward-only, so the original file's comment is left as a historical artifact rather than edited in place; the corrected, current meaning is set as a real, live `COMMENT ON COLUMN audit_events.actor_user_id IS ...` (`modules/audit/migrations/20260824090100_audit__document_actor_user_id_for_unresolved_actors.sql`) — one place this now lives, queryable from the database itself, superseding the stale prose rather than duplicating an explanation in a second doc file.

**(c) `RISK_REGISTER.md` R-003's status corrected from `RESOLVED` to `ACCEPTED`.** The 2026-08-23 update evaluated both named alternatives to the `memberships`/`store_memberships` self-access RLS clause and kept the clause permanently — but `RESOLVED` reads as "the risk is gone" to a future phase-gate review, when the actual outcome is "the risk is retained by design, having been weighed against its alternatives." Status text corrected with one clarifying sentence; the surrounding evaluation itself is unchanged.

**Also touched, mechanically:** none — unlike `auth.login`, this slice needed no entity widening and no existing test file required a code change, by construction of decision 2.

**Status:** RESOLVED for all eight decisions and all three corrections.

## 2026-08-23 — `auth.login`: ten decisions for the most divergent capability in the codebase

**Context:** implementing Task 2 slice 5's first of three capabilities (`08_PHASE_1_BRIEF.md` §3). Every prior slice mirrored the golden path with at most two documented divergences (`organization.create`'s missing guard and permission). This capability has almost no pipeline before it at all — there is no session to authenticate, no tenant to resolve, no permission to check — and forces three structural questions none of the previous four slices raised. Per the `/new-slice` skill's own instruction for this case: documented here, not solved by inventing a second pipeline shape.

**1. Which pipeline steps survive.** Written out explicitly rather than claimed as a mirror:
  - **Step 1** does not apply — this capability IS what creates a session, from the opposite direction `SessionGuard` authenticates one.
  - **Steps 2–4** do not apply — `auth.login` is `05` §4.1's `global` scope; there is no organization, no store, and nothing to resolve access to.
  - **Step 5 (transaction + RLS)**: no transaction is opened at all. `users`, `credentials` and `sessions` are all RLS-exempt (see decision 3), so there is no tenant context to establish, and the only write is one `INSERT` into `sessions`, atomic on its own with no second statement to coordinate it with. `platform/db/tenant-context.ts` remains the only place a transaction is EVER opened in this codebase (ADR-030's singleton rule) — this capability simply never needs one, the same way `SessionGuard`/`UserRepositoryPg` already read `users`/`sessions` through the plain `APP_DB` connection with no `withTenantContext` call. Wrapping a no-op transaction around this work purely to resemble the other slices would be theater, not architecture.
  - **Step 6** does not apply — there is no membership yet for a permission check to read, the same structural reason `organization.create` declares `requiredPermissions: []`.
  - **Steps 8–10 apply unchanged**: one durable audit event on `AUDIT_DB`, both outcomes (decision 2 covers WHICH tenant it is written under); the stable error envelope; structured logging, with `tenantId: null` in the log line — honestly, since none exists (see decision 2's note that the audit sentinel is a storage device, never surfaced to the logger).
  - **Step 11** applies as always.

**2. The audit event: `audit_events.tenant_id` is `uuid NOT NULL`, and this capability has no tenant.** A NULL column would satisfy the existing RLS policy's comparison under NO context, ever — making such a row permanently unreadable, not merely hidden by default. Full reasoning, options, and the accepted residual cost are in **ADR-035** (new — this rose to ADR level, not a decision-log entry, because it governs audit representation for every future global/tenant-less-at-entry capability: `auth.logout`, `auth.logout_all`, and `organization.switch` all inherit it, exactly the cross-cutting reason ADR-034 existed for audit placement generally).
  **Decision: a reserved sentinel tenant id**, `00000000-0000-0000-0000-000000000000` (`PLATFORM_TENANT_ID`, `modules/audit/domain/audit-event.entity.ts`). No schema change, no RLS policy change — reading these rows back is `withTenantContext(db, { tenantId: PLATFORM_TENANT_ID, ... })`, the identical helper every other tenant's rows go through. The sentinel is an audit-storage device only: never attached to `request.tenantContext`, never logged, never returned to a client — proven directly by a test asserting the structured log line for this route carries `tenantId: null`, not the sentinel.

**3. `credentials` tenancy — the forcing point R-003 named this slice as.**
  - **Decision:** exempt, joining `users`/`sessions`/the role catalog. Same reasoning as `sessions`: a password belongs to the person, not to any organization they hold membership in, and RLS here would be circular for the identical reason it would be on `sessions` — verifying a credential is part of the step that establishes which tenant is trusted in the first place. `identity_providers` is NOT created — this capability (password-only login) does not need it, and `AGENTS.md` §4 forbids building ahead of a genuine need; its tenancy stays undecided.
  - **This changes a normative document**, not just code, so it was changed in this same commit rather than left to drift (`PHASE_1_GATE_REVIEW_2026-08-22.md` Finding 2 was exactly a code/document disagreement of this shape): `08_PHASE_1_BRIEF.md` §5's exemption list now names `credentials`; `.claude/skills/new-slice/SKILL.md` Step 4's exemption list does too; `tools/conformance/rules/schema.ts` and `schema-live.ts`'s `TENANT_EXEMPT` sets both gained `credentials` — the harness flagged `credentials` for missing `tenant_id`/RLS the first time `npm run conformance` ran against this slice's migration, confirming the mechanical check actually catches an exemption-list gap rather than only ever passing.
  - **R-003 re-evaluation** (RISK_REGISTER.md, updated in the same commit): the self-access RLS clause on `memberships`/`store_memberships` is **kept**, not because this slice avoided the question but because both named alternatives were evaluated on their merits and rejected. (i) A `SECURITY DEFINER` bootstrap function remains uncoupled to this slice's decision and unbuilt — nothing here forces it, and it would trade the current narrow, already-tested RLS surface for a new privileged-function trust boundary with no offsetting need. (ii) "An authoritative tenant on the session row" — the alternative R-003 explicitly named as coupled to this slice — turns out not to be available even now: `sessions.active_organization_id` already exists, but ADR-002 and ADR-029 item 5 are explicit that it is session state, a UI convenience, never authority for tenant resolution, and trusting it as authoritative would mean either accepting a staleness window if a membership is revoked after the column was last set (a real security regression: ADR-029's own verification list requires "cached membership invalidates on membership change") or re-querying `memberships` to confirm it is still valid anyway — which is the exact bootstrap read the self-access clause already exists to permit, just relocated. Neither alternative removes the need for the clause; one is unbuilt and uncoupled, the other was never actually viable. R-003's status is updated to reflect a completed evaluation, not a further deferral.

**4. Argon2id (ADR-029 item 2).** `@node-rs/argon2` (napi-rs, prebuilt binaries per platform via `optionalDependencies`, `win32-x64-msvc` included), not the classic `argon2` package, which has historically needed node-gyp and a C++ toolchain on a platform with no matching prebuilt binary. This machine is Windows with no Docker and no guaranteed build toolchain — installed and hash/verified with the real package on this exact machine before committing to it, not assumed to work from documentation. Parameters: `memoryCost: 19456` KiB (19 MiB), `timeCost: 2`, `parallelism: 1` — OWASP's current minimum recommended Argon2id profile, a defensible cited floor since neither ADR-029 nor any other document fixes numbers. Tuned for a moderate per-login latency budget (observed 14–27ms in the integration suite on this machine), not maximum resistance; revisit with real capacity numbers before meaningful login volume.

**5. What login returns, and how the session reaches the client.** Cookie: `httpOnly: true`, `secure: true`, `sameSite: "lax"`, `path: "/"`, `maxAge` equal to the session's real server-side lifetime (30 days — fixed here since no document sets one; there is no sliding-expiration or refresh mechanism for browser sessions in Phase 1). `secure: true` is set **unconditionally**, exactly as ADR-029 item 3 requires, even though the test suite runs over plain HTTP: every test authenticates by copying the `Set-Cookie` value into a `Cookie` header by hand (supertest has no browser-style cookie jar that would refuse to send a `Secure` cookie over HTTP), so this required zero conditional/environment-dependent logic and breaks nothing locally; a real browser only ever sends it back over HTTPS, which production termination provides. Response body: `userId`, `email`, `displayName`, `activeOrganizationId` (decision 8), `sessionExpiresAt` — never the raw token, never a password hash. `sessions.token_hash` is the only place any form of the token is stored; the raw value exists only in the cookie for the instant it is minted and returned.

**6. Failure indistinguishability.** Unknown email, wrong password, and a suspended user all return the identical `AUTHENTICATION_REQUIRED` / 401 with the identical message string — same precedent `ValidateSessionService` already established for session validation, same reason: distinguishing them would hand an attacker an account-enumeration oracle. Timing is closed the same way: every non-success path performs exactly one `PasswordHasher.verify()` call, against the real stored hash when a credential exists or `DUMMY_PASSWORD_HASH` (a precomputed literal, same algorithm and parameters, `modules/identity/domain/password-hasher.ts`) when none does — an unknown email that skipped hashing entirely would return measurably faster than a wrong password for a real account. Proven three ways: a unit test asserts exactly one `verify()` call across all four non-success branches; a unit test asserts `DUMMY_PASSWORD_HASH` specifically is what gets checked when no credential exists; an integration test samples real request latency for "unknown email" vs. "wrong password, real account" and asserts the medians are within the same order of magnitude, not merely "both slow."

**7. Rate limiting and lockout: absent, and this is stated plainly rather than quietly shipped.** ADR-029 item 2 requires "failed attempts are rate-limited per identifier and per IP"; `05` §5's `CapabilityDefinition` shape names a rate limit field; `CapabilityDefinition` (`modules/capability/domain/capability-definition.ts`) deliberately omits it, the same "don't declare a field nothing enforces" reasoning that already omits `entitlements`/`quota`/`approval`. No module-local throttling is built here — `AGENTS.md` §4's idempotency reasoning applies in spirit: a rate limiter is exactly the kind of shared, cross-capability concern (rate limiting per tenant, per user, per IP is called out in `01_ARCHITECTURE_BASELINE_RFC.md`) that must not be invented locally inside one capability, and building a real one is out of scope for a single Task 2 slice. **`auth.login` ships with no brute-force protection.** Added to `RISK_REGISTER.md` as R-005.

**8. `active_organization_id` on the new session.** **Decision: always `null`.** The alternative — auto-selecting the user's sole membership's organization if they have exactly one — was considered and rejected: it would require `modules/identity` to query `modules/tenant`'s `memberships` table, a dependency edge that does not exist today (`identity` depends only on `capability`, now also `audit`; `tenant` depends on `identity`, never the reverse) and would need to be built through `modules/tenant/contracts` for a value ADR-002 already states is "a UI convenience," never authority. The convenience is not worth a new, backwards-facing cross-module dependency in the one capability that establishes a session before anything else exists. Confirmed by the project graph diff: `identity`'s only new dependency from this slice is `audit`, not `tenant`.

**9. Idempotency.** `05` §4.1 gives `auth.login` `LOW_WRITE` and idempotency `no` — the first capability in Task 2 with **no divergence to record**: declared `idempotent: false` because that is what §4.1 actually says, not a workaround for ADR-009 being Phase 2. Confirmed rather than assumed, to avoid copying the previous four slices' boilerplate reflex onto a row that does not need it.

**10. Seeding.** Added `seedCredential(db, userId, plainPassword)` to `apps/api/test-support/seed.ts`, not folded into `seedUser` and not a plaintext/fake shortcut. Folding it into `seedUser` would add a real Argon2id hash (14–27ms of wall-clock work) to every test in the suite that seeds any user, the overwhelming majority of which never touch `auth.login` at all. It hashes through the real `Argon2PasswordHasher`, not a stand-in, so `auth.login`'s own tests exercise the genuine `verify()` path end to end — the "slower but honest" option, deliberately, over a plaintext comparison that could silently diverge from what production actually does. Every existing test that seeds a user continues to pass unchanged; none of them call the new helper.

**Also touched, mechanically:** `User` widened to carry `email`/`displayName` (needed for the login response), `Session` widened to carry `tokenHash`/`createdAt` and `SessionRepository` gained `create()` — both entities' existing call sites (`validate-session.service.spec.ts`, `session.entity.spec.ts`, `invite-member.service.spec.ts`, `user.repository.pg.ts`, `session.repository.pg.ts`) updated for the new constructor shapes, the same mechanical widening every prior slice's port changes have required. `login.service.spec.ts`'s own fixture password was written with a space (`"correct horse battery staple"`) rather than a hyphenated no-whitespace string, after the first version tripped `SECRET-CREDENTIAL-LITERAL` — the scanner's regex specifically excludes whitespace because that is the shape a real leaked token or password has, and a multi-word test fixture correctly falls outside it; the explanatory comment itself had to be reworded once more after its own quoted example reproduced the flagged shape.

## 2026-08-23 — A path parameter is authoritative; a differing body value is rejected, not silently overridden

**Context:** independent review of `store.create`'s guard change (2026-08-23, "store.create: the route...") flagged that `OrganizationAccessGuard`'s path-then-body fallback, and the identical `{ pathParams, ...body }` spread `membership.controller.ts` and `membership-role.controller.ts` build for their own Zod input, both let a body key with the SAME name as a path parameter silently win, because the body is spread last in a plain object literal. Confirmed empirically before any fix, per `AGENTS.md` §5's "do not take a description as established fact":

- `membership.role.assign`, path `membershipId` = X, body `{ roleKey, membershipId: Y }` (Y a different, same-tenant membership): the role was granted to **Y**, not X. The response's `membershipId`, the `membership_roles` row, and the audit event's `resource_id` and `metadata.targetMembershipId` all named Y. The URL the caller sent named X; nothing that happened matched it. **This is the real defect** — the value a reviewer would read off the URL and the value actually acted on could differ.
- The same route with a differing `organizationId` also present in the body (caller a member of both organizations): the write landed in the PATH's organization, not the body's — `parsed.data.organizationId` was validated as a well-formed UUID and then never read again; `tenantContext.tenantId`, resolved by the guard from the path before the controller ever parses the body, is what every downstream write and the audit row actually use. **Not a cross-tenant bypass** — the guard's path-derived tenant was authoritative in practice even before this fix — but the API silently tolerated two disagreeing explicit inputs rather than saying so.
- `membership.invite` behaves identically for `organizationId`, for the same reason (its schema has no target-id field to reproduce the more serious `membershipId` finding).

**Options considered:** (A) leave path-wins-silently as is, since the tenant-scoping half was never actually exploitable; (B) fix only the `membershipId` case (the one with real consequence) and leave `organizationId`'s silent-tolerance as is; (C) adopt one rule for every path-and-body key on every route: a differing body value is rejected outright, not resolved by precedence.

**Decision: C.** `08_PHASE_1_BRIEF.md` §5 requires a resource id to be an explicit input; ADR-002 requires it never be inferred. Two explicit inputs disagreeing is neither of those things — it is an ambiguity, and resolving it silently in whichever direction an object literal happens to spread last is a decision the server was making without anyone having decided it. Rejecting is the only resolution that cannot surprise a reader of the URL, and it is also the only one that guarantees the value a guard already authorized is identical to the value a service acts on and an audit row names — which is precisely the property the `membershipId` finding shows can otherwise break. (B) was rejected because the `organizationId` case is the same ambiguity in miniature and leaving it tolerated would mean the rule applied inconsistently within the very code that states it.

**Identical duplicates are accepted, not rejected.** A body that repeats the same key with the SAME value as the path has made no error — rejecting an exact echo would only train clients to strip it defensively before every call, for no safety gained.

**Implementation, one shared function, not three copies (`AGENTS.md` §2):** `modules/capability/interfaces/path-body-conflict.ts` — `resolvePathOrBodyValue(key, pathValue, body)` (the single-key primitive; throws `CapabilityError("VALIDATION_ERROR", ...)` on a differing pair) and `buildValidationInput(route, pathParams, body)` (applies it to every key in `CapabilityDefinition.route.pathParams`, driven by that declaration rather than a hand-written per-controller list, so a future capability that forgets to think about this still gets it for free). Placed in `modules/capability`, not `modules/tenant/interfaces`: this is a generic controller-pipeline concern with no tenant/organization semantics of its own — any future module whose route mixes a path parameter with a body needs the identical rule, and `modules/capability/interfaces/` already holds the one other cross-cutting interfaces-layer file (`http-exception.filter.ts`). Re-exported through `modules/capability/contracts/index.ts`, same as everything else another module is allowed to reach.

Applied to: `OrganizationAccessGuard` (its own comment previously said the path-then-body ordering was "unexercised in practice, not load-bearing" — that stopped being true the moment anything actually compared the two rather than ignoring the second once the first was found); `membership.controller.ts` (`organizationId`); `membership-role.controller.ts` (`organizationId`, `membershipId`). **Not applied to** `organization.controller.ts` or `store-create.controller.ts` — both parse the raw body directly with zero path parameters (`route.pathParams: []`), so `buildValidationInput` would be a verified no-op there; left calling `.safeParse(body)` untouched rather than routing them through the helper for its own sake. **Not applied to** `store.controller.ts` (the golden path) — confirmed by inspection, not assumed, that it has no `@Body()` decorator and no path-plus-body merge of any kind (`GET`, no body): it does not exhibit the pattern and needed no change.

**Regression tests, shown to fail before the fix and pass after** (stashed the six changed/added implementation files, keeping the new tests, ran them, restored the stash): a differing `membershipId` on `membership.role.assign` → 400/`VALIDATION_ERROR`, no role granted to either membership named, no audit row; a differing `organizationId` on the same route, and on `membership.invite` → 400/`VALIDATION_ERROR`, no membership/role created in either organization, no audit row under either tenant; an *identical* duplicate on both routes → 201, unaffected (these two passed even before the fix, since that path was never broken — included to pin the accepted case, not as defect evidence). All four capabilities' full existing suites, including `store.create`'s reliance on the guard's body fallback, pass unchanged.

**Status:** RESOLVED.

## 2026-08-23 — `store.create`: eight decisions, including the first route that breaks the established convention

**Context:** implementing Task 2 slice 4 (`08_PHASE_1_BRIEF.md` §3). Better documented than the previous three slices in one specific way — `05_API_CAPABILITY_CONTRACTS.md` §6.1 gives this capability an explicit worked contract, the first of the four Task 2 capabilities to have one — but otherwise raises the same category of open questions.

**1. The route.** §6.1 states, literally: `POST /api/v1/stores` with body `{ organizationId, name, slug }`. But `OrganizationAccessGuard` (built for `membership.invite`, reused by `membership.role.assign`) reads `organizationId` only from `request.params["organizationId"]` — it cannot resolve a body field as written, and both prior slices nested the organization in the path (`/organizations/{organizationId}/...`) for internal consistency, with no normative document actually requiring that shape.
  **Options considered:** (A) follow §6.1 literally — flat route, `organizationId` in the body — and extend `OrganizationAccessGuard` to accept either location; (B) nest it as `POST /api/v1/organizations/{organizationId}/stores` for consistency with slices 2–3, recording a divergence from §6.1.
  **Decision: A.** The precedence chain (`README_START_HERE.md`, `AGENTS.md` §1) ranks Contract-tier documents above internal consistency with a pattern that was never itself a written rule — slices 2–3's path-based shape was a convention adopted for lack of a stronger signal, not a decision anything documents. §6.1 is that stronger signal, and it is unambiguous. A body field is still "an explicit application-level input" under ADR-002 — the rule that matters is "never derived from the token," which holds equally for a path segment and a body field.
  **Implementation:** `OrganizationAccessGuard` now reads `request.params["organizationId"] ?? request.body?.organizationId`. Path wins when both are present, which matters to no existing route today (none supplies both) — the ordering exists only because that is what `membership.invite`/`membership.role.assign` already depend on structurally. **Proven not to regress those two slices**: their full existing test suites (49 tests across `membership-invite.integration.spec.ts` and `membership-role-assign.integration.spec.ts`) pass unchanged, with no test file touched.
  **Consequence for §6.1 and for internal consistency:** nothing needs to change in `05` — this slice conforms to it. What is now visibly true is that the four Task 2 capabilities do not share one routing convention: `organization.create` and `store.create` are flat with body-supplied scope; `membership.invite` and `membership.role.assign` are path-nested. That inconsistency is a direct, traceable consequence of `05` giving an explicit contract for exactly two of the four (`organization.create` has none either, which is why it was free to be flat) and staying silent on the other two, not an oversight introduced here. A future slice with its own explicit `05` contract should follow that contract the same way, even if it disagrees with whatever convention the silent slices established.

**2. Does creating a store also make its creator a store member?** 08 §5: "`store_memberships` is checked for every store-scoped read; organization membership alone is not sufficient." Without a `store_memberships` row, the creator could not `store.read` the store they just made — the golden path would be unreachable for a freshly-created store.
  **Decision:** yes, in the same transaction as the store. The organization.create precedent one level down: that slice wires in an ACTIVE membership + owner role because a roleless organization is unusable; this one wires in a `store_membership` row because a store with no store-member is unreachable by its own creator. No per-store role catalog exists to grant into, so there is nothing analogous to owner-role-granting here — one row is the whole of it.
  **Proven, not just asserted:** `apps/api/store-create.integration.spec.ts`'s "lets the creator immediately store.read the store they just created" test drives both capabilities through real HTTP in one test — the first test in this codebase to do so — and is the single best evidence this decision is correct, per the implementing instruction's own framing.

**3. `reserved_subdomains`: ownership, shape, seed, exemption, and check ordering.**
  - **Ownership:** `modules/tenant/migrations/`, not a new `domains` module. `04_DATABASE_BLUEPRINT.md` §2.1 sketches it near the Phase 4 domains cluster, but its only Phase 1 consumer is store slug validation inside `modules/tenant`, and `AGENTS.md` §4 forbids creating a module for anything in `future/`. Exact precedent: `currencies` (also conceptually platform-wide) lives under `modules/money` because money was its only Phase 1 consumer.
  - **Shape:** `reserved_subdomains (name text PRIMARY KEY)` — matches 04 §2.1's minimal sketch ("`reserved_subdomains -- name`"), nothing more.
  - **Seed:** `www, api, admin, app, mail, static, cdn, assets, status, docs, blog, help, support` — thirteen names, chosen because a platform offering subdomains conventionally withholds exactly this class of name (so it cannot later collide with a service the platform itself needs to host there — a status page, API docs, a CDN endpoint, an admin console). Not random, not exhaustive: the migration comment states explicitly that the list is expected to grow before Phase 4's host resolution (ADR-028) ships.
  - **Exemption:** confirmed explicitly in the migration comment, citing 08 §5's exemption list by name — not left for a reader to wonder whether omitting `tenant_id`/RLS was forgotten.
  - **Where the check lives:** a repository read (`ReservedSubdomainRepository.isReserved`) plus a single `if` in `CreateStoreService`, not a database constraint. A Postgres CHECK constraint cannot reference another table; a trigger enforcing this would put authoritative business logic in the database, which `AGENTS.md` §4 forbids outright. **Consequence stated explicitly:** adding a word to the list later does not retroactively invalidate a store already using it — this is a create-time gate, not an ongoing constraint — and this slice does not attempt retroactive enforcement.
  - **Case handling:** the reserved check runs AFTER normalization. `createStoreInputSchema`'s Zod `.trim().toLowerCase()` runs first (mirroring `organization.create`'s slug rule exactly), and the seed is written in that same lowercase, trimmed form, so the comparison is a plain equality with nothing to drift. Proven directly: a test submits `"  ADMIN  "` and asserts `DOMAIN_RESERVED`, not a slug-format `VALIDATION_ERROR` and not a false negative from case mismatch.

**4. Which error code a reserved slug returns.** §7 lists `DOMAIN_RESERVED`; the alternatives were reusing `VALIDATION_ERROR` (a slug-format problem, which this is not — a syntactically valid slug can still be reserved) or `CONFLICT` (already claimed by the duplicate-slug case).
  **Decision:** add `DOMAIN_RESERVED` to `CapabilityErrorCode`, mapped to HTTP 409 — the most precise of the three options, and §7 already permits it. Given the same status as `CONFLICT` (both are "this value conflicts with something the system already knows," just a reserved word instead of another row) but kept as a distinct code, so a client can tell the two apart without parsing the message. The ADR-033 generator collapses same-status codes into one documented response per status with each code named in the description — confirmed directly: `POST /api/v1/stores`'s `409` response documents `"CONFLICT | DOMAIN_RESERVED"`.

**5. The `store.create` permission.** §4.1 rates it MEDIUM_WRITE — `membership.invite`'s tier, not `membership.role.assign`'s HIGH_WRITE.
  **Decision:** granted to `owner` and `admin`, exactly matching `membership.invite`'s precedent, for the same reason: creating a store is an administrative act inside an existing organization, not a top-tier action. `membership.role.assign`'s owner-only restriction exists specifically to close a self-escalation path (granting a role) that creating a store has no equivalent of, so there is no reason to import that restriction here. A plain `member` does not hold it — new migration, permission only, `ROLE_KEYS` and the `roles` table are untouched, so `role-catalog-agreement.spec.ts` has nothing new to disagree about.

**6. Slug uniqueness scope: a real forward-looking conflict, flagged and not solved.** `04` §5's `UNIQUE (tenant_id, slug)` is per-organization, exactly as required — but `reserved_subdomains` exists because a store slug is expected to become a subdomain, and a subdomain namespace is inherently global. Two organizations can each hold a store slugged `shop` today (proven directly by this slice's own "the SAME slug succeeds in a DIFFERENT organization" test), which per-organization uniqueness explicitly permits and a shared subdomain namespace would not.
  **Decision: flag, do not solve.** ADR-028's host resolution (platform-global hostname uniqueness for *verified custom domains*) is Phase 4, and nothing in the docs pack states that platform-provided subdomains (as opposed to custom domains) are even in scope for ADR-028 as written — which is precisely why this is a real open question rather than something ADR-028 already answers. Recorded here **and** in `RISK_REGISTER.md` as R-004, so Phase 4 meets this as a documented decision point rather than a discovery. Not touching the index and not designing a resolution now, per the instruction and per `AGENTS.md` §4's prohibition on building for `future/`.

**7. Idempotency.** §4.1 says yes; ADR-009's shared store is Phase 2.
  **Decision:** `idempotent: false`, the same divergence the three prior slices recorded, for the same reason — declaring `true` would publish an `Idempotency-Key` guarantee nothing provides. `UNIQUE (tenant_id, slug)` means a naive retry returns `CONFLICT` rather than creating a duplicate. Flip belongs to the ADR-009 slice, on all **four** capabilities together now.

**8. `storeScoped`.** This capability creates a store; it does not act inside one.
  **Decision:** `storeScoped: false`. `rlsContext.storeId` stays `null` throughout the controller (the same pattern `organization.create` uses), so `app.store_id` is never set for this operation — `04` §5's store-scoped RLS note does not apply here because this is not a store-scoped operation, and nothing in the implementation contradicts that declaration.

**Status:** RESOLVED for decisions 1–5, 7 and 8. Decision 6 is flagged, deliberately unresolved, tracked in both this log and `RISK_REGISTER.md` (R-004) pending Phase 4.

## 2026-08-23 — `membership.role.assign`: ten decisions, the largest open surface of any slice yet

**Context:** implementing Task 2 slice 3 (`08_PHASE_1_BRIEF.md` §3). Documented no more thickly than `membership.invite` was: one row in `05_API_CAPABILITY_CONTRACTS.md` §4.1 (`membership.role.assign | tenant | HIGH_WRITE | yes`) and one step in `03_TECHNICAL_BLUEPRINT.md` §167's flow. No route, no request/response shape, no statement of add-vs-replace semantics, no statement of who may call a HIGH_WRITE capability, and one non-negotiable phase rule (§5's session-invalidation-on-role-change) with no capability yet built to satisfy it. Ten questions, addressed in the order the implementing instruction posed them.

**1. Route and HTTP shape.** Nothing specifies one; `organizationId` must stay an explicit path parameter (ADR-002) and the target membership must be explicit too (never inferred, matching `storeId`'s treatment throughout).
  **Decision:** `POST /api/v1/organizations/{organizationId}/memberships/{membershipId}/roles`, body `{ roleKey }`. A nested resource under the existing `memberships` route, consistent with `membership.invite`'s own placement one level up. A separate controller (`MembershipRoleController`), not a second method on `MembershipController`: every capability so far is one controller class with one method, and growing an existing controller's guard/DI surface for an unrelated capability would break that 1:1 mapping silently.

**2. Add-one-role vs. replace-the-set.** The capability id is singular ("assign"); `membership_roles` allows several rows per membership; the three-role catalog is owner/admin/member.
  **Decision: add one role.** `03` §167's flow ("invite member → assign role") describes granting a member's first role, not resetting an existing set, and nothing in the pack implies a replace/reset operation. A `POST` that inserts one row is also the simpler, less error-prone shape — a replace would need an atomic delete-then-insert with its own "what if the set becomes empty" question, unforced by anything in the brief. The DTO names one grant (`MembershipRoleDto`: id, organizationId, membershipId, roleKey, createdAt), not a roles array, making the choice visible rather than implied.

**3. Who may call it, and why HIGH_WRITE buys nothing extra yet.** §4.1 rates this HIGH_WRITE while `membership.invite` is MEDIUM_WRITE (owner+admin); an admin holding this permission could grant `owner` to themselves or anyone, escalating past their own ceiling, and `CapabilityDefinition` has no `approval` field to gate on even if ADR-001's Phase 9 approval flow existed today.
  **Decision:** grant `membership.role.assign` to `owner` ONLY (`20260823100000_authorization__add_membership_role_assign_permission.sql`), not admin. This sidesteps the escalation question entirely rather than attempting per-target-role restriction logic this phase has no machinery for (no approval step, no "you may only grant a role at or below your own" rule engine). **Recorded explicitly so a later reader does not assume a control exists**: HIGH_WRITE today is enforced purely by which roles hold the permission — identical mechanism to MEDIUM_WRITE and LOW_WRITE. No additional confirmation, rate limit, or approval step exists for any risk tier; the field is documentation of intent until Phase 9.

**4. Unknown/invalid role key.** Only codes already in `capability.errors.ts` may be used; §7 must already list one.
  **Decision:** `VALIDATION_ERROR`, produced at the Zod schema boundary, not a new domain error. `roleKey` is validated against `z.enum(ROLE_KEYS)`, where `ROLE_KEYS = ["owner","admin","member"] as const` (new: `modules/authorization/domain/role-key.vo.ts`) mirrors the closed, platform-global catalog `04_DATABASE_BLUEPRINT.md` and the permission-catalog migration already establish — Phase 1 has no tenant-custom roles, so the catalog IS this fixed list, not something to discover per-request. `RoleGrantRepositoryPg`'s own catalog lookup can still fail (`RoleNotInCatalogError`) if the seed is ever corrupted, but that path is structurally unreachable through the API once the schema restricts input, and is left to fall through to the generic `INTERNAL_ERROR` path (same as any unmapped repository error) rather than special-cased.

**5. Target membership missing, wrong tenant, or REVOKED.** Slice 2's `ResolveOrganizationAccessService` treats "no membership" and "revoked membership" identically (`FORBIDDEN`) so a former member cannot use the difference to confirm an organization exists.
  **Decision: follow that precedent, consciously, for all three cases — one code, `RESOURCE_NOT_FOUND`.** `MembershipRepository` gained `findById(id)`, resolved inside the transaction (step 7, mirroring how the golden path resolves the store ENTITY inside `ReadStoreService` while the guard only checks the caller's own access) rather than in the guard. `AssignMembershipRoleService` checks `!target || target.tenantId !== command.tenantId || !target.isActive` as one condition, one message, one code.
  **A real finding surfaced while designing this, not merely a defensive habit:** `memberships`' RLS policy carries the self-access OR clause (RISK_REGISTER.md R-003) — `USING (tenant_id = current_tenant OR user_id = current_user)`. A caller who is `owner` of organization A and *also* a member of organization B can name organization B's membership id (their own row there) while acting under organization A's tenant context, and `findById` **will return that row**, because the `user_id` branch of the policy matches regardless of which tenant is current. Without an explicit `target.tenantId !== command.tenantId` check, this service would silently operate on a membership in the wrong tenant. The check is load-bearing, not decorative — documented inline on the port (`membership.repository.ts`) and proven directly: `apps/api/membership-role-assign.integration.spec.ts` seeds exactly this scenario (a caller who owns two organizations, naming the second org's membership id while acting in the first) and asserts `RESOURCE_NOT_FOUND` with no grant written.

**6. Duplicate grant.** Slices 1–2 both chose the unique index over a SELECT pre-check, mapping the violation to `CONFLICT` via `platform/db/constraint-violation.ts`.
  **Decision: follow it.** `UNIQUE (membership_id, role_id)` on `membership_roles` is the only race-free authority; `RoleGrantRepositoryPg` catches `membership_roles_membership_id_role_id_key` and raises the new `RoleAlreadyGrantedError`, which the service maps to `CONFLICT`. No departure from precedent here — nothing about this slice's shape argues for one.

**7. Idempotency.** §4.1 says yes; ADR-009's shared store is Phase 2; `AGENTS.md` §4 forbids a module-local substitute.
  **Decision:** `idempotent: false`, the same divergence recorded on `organization.create` and `membership.invite`, for the same reason — declaring `true` would publish a client-visible `Idempotency-Key` guarantee nothing provides. The unique index already makes a naive retry return `CONFLICT` rather than double-granting. Flip belongs to the ADR-009 slice, on all three capabilities together.

**8. What HIGH_WRITE does and does not buy today.** Covered substantively under (3); recorded here as its own checklist item per the instruction. **Does not buy:** approval workflow (ADR-001, Phase 9), additional authentication step, rate limiting, or any runtime behavior distinct from MEDIUM_WRITE/LOW_WRITE. **Does buy:** nothing beyond documentation intent and the permission-catalog decision this slice makes (owner-only) as a substitute control. A future reader must not assume `risk: "HIGH_WRITE"` alone changes what the pipeline does.

**9. Session invalidation on role change — decided per AGENTS.md §5, chosen: implement now (Option A).**
  Facts established before deciding: `ValidateSessionService` checks only the session's own validity and the user's status, never memberships — so a role change is *authorization-effective* immediately regardless, but a session token issued before the change keeps working until it separately expires. `sessions` already has `status`/`revoked_at`; no schema change needed. `SESSION_INVALIDATED` exists in `capability.errors.ts` and §7, unused until now (this slice still doesn't surface it as a client-facing code — the target simply gets `AUTHENTICATION_REQUIRED` on their next request via the existing `isValid()` check, which is the correct read: from the target's perspective their session is gone, not merely "invalidated" in some intermediate sense `SESSION_INVALIDATED` would need to distinguish). `membership.revoke` — the capability the phase-brief exit criterion (§6 row 4) is actually worded about — is **not** one of the six Task 2 slices.
  **Options considered:** (A) implement now, a real port (`SessionRevocationRepository`, `modules/identity`), called inside the same transaction as the role grant, proven by a test that uses the target's cookie again after the change. (B) record OPEN, defer to `membership.revoke`, on the theory that a partial implementation (1 of 3 triggers: password change, membership revocation, role change) invites false confidence.
  **Decision: A.** The deciding fact is that `membership.role.assign` is the **only** point among all six Task 2 slices where "role change" can occur at all — `membership.revoke` isn't scheduled, and no password-change capability is among the six either (`auth.login`/`logout`/`logout_all` don't include one). Deferring here does not defer the obligation to a later slice that will pick it up; it very plausibly means the "role change" trigger never gets built during Task 2's announced scope at all. Given §5 states this as a **non-negotiable rule for this phase**, not an aspiration, building it in the one slice that can is judged safer than the false-confidence risk (B) warns about — which is mitigated instead by stating precisely, here and in CLAUDE.md, which of the three triggers are covered (role change: yes, this slice) and which are not (password change, membership revocation: no capability exists yet for either).
  **Design:** `SessionRevocationRepository.revokeAllForUser(userId, revokedAt)`, exported from `modules/identity/contracts/`. Scoped by `userId` alone, not by organization — `sessions` carries no `tenant_id` (one live session spanning every organization a user belongs to, per the earlier sessions-tenancy decision), so an organization-independent trigger correctly invalidates everywhere, not narrowly. Called from `AssignMembershipRoleService` on the SAME transaction/connection as the role grant (not a second `withTenantContext` call), so the two writes are atomic: a grant that landed without its required invalidation, or the reverse, would each be a correctness bug the phase rule exists to prevent. Applies even to self-assignment — a caller granting themselves a role revokes their own current session too, an accepted consequence rather than a special case, proven directly by test.
  **Side effect surfaced while building this:** `modules/identity/infrastructure/identity.tables.ts`'s `revoked_at` column was typed `ColumnType<Date, string | undefined, never> | null` — the `| null` wrapped OUTSIDE the `ColumnType`, which made Kysely's Insertable/Updateable extraction distribute over the union and land on `null` as the only legal update value, blocking `UPDATE sessions SET revoked_at = ...` entirely. Fixed by folding nullability into the `ColumnType` itself (`ColumnType<Date | null, string | null | undefined, string | null>`), the idiomatic Kysely form. Not a defect in the original slice — nothing before this one ever updated `sessions` after insert, so the restrictive type was accurate until now.
  **Status:** the role-change trigger is RESOLVED (implemented, tested). Password-change and membership-revocation triggers remain **OPEN** — the former has no capability in Phase 1's six slices at all; the latter belongs to `membership.revoke` (outstanding exit criterion, not scheduled).

**10. Self-assignment and the "last owner" question.**
  *Self-assignment*: explicitly allowed, no special case. Only `owner` may call this capability (decision 3), and owner is already the top of the catalog, so a caller granting themselves an additional role (e.g., an owner also taking `admin`) cannot escalate past a ceiling they are already at — there is no privilege-escalation vector to close. The one real consequence — the caller's own session gets revoked mid-flow by decision 9's mechanism — is accepted, not suppressed (see decision 9's "self-assignment" note), because suppressing it for the self-case would be inconsistent enforcement of a rule §5 states unconditionally.
  *"Last owner" protection*: **explicitly out of scope for this slice**, not merely unaddressed. This capability only ever ADDS a role (decision 2) — it has no mechanism to remove or demote anyone's existing roles, so it cannot reduce an organization to zero owners under any input. The "last owner" invariant only becomes meaningful for a future role-*removal* capability, which is not among the six Task 2 slices and does not exist yet.

**Status:** RESOLVED for decisions 1–8 and 10. Decision 9 is RESOLVED for the role-change trigger and OPEN for the other two triggers of the same phase rule, tracked here and in CLAUDE.md rather than assumed closed.

## 2026-08-23 — `membership.invite`: what "invite" can mean in Phase 1

**Context:** implementing Task 2 slice 2 (`08_PHASE_1_BRIEF.md` §3). This capability is documented more thinly than any so far: one row in `05_API_CAPABILITY_CONTRACTS.md` §4.1 (`membership.invite | tenant | MEDIUM_WRITE | yes`), one step in `03_TECHNICAL_BLUEPRINT.md` §167's flow ("create organization → **invite member** → assign role → create store → read store"), one bullet in `00_PLATFORM_OVERVIEW.md` §58 ("invite team members"), and one mention in `01_ARCHITECTURE_BASELINE_RFC.md` §483 listing *invitation* among the required V1 notification flows. There is no request/response contract, no state machine, and no `invitations` table anywhere in `04_DATABASE_BLUEPRINT.md` §2.1.

**1. Is this a real invitation (offer → accept) or an immediate add?** The distinction decides the whole slice.
  - Options: (A) a genuine invitation — needs an `invitations` table, which `08` §4's scope list does not contain and §4 forbids creating ("Only these. Creating anything else is out of scope"); (B) a pending membership — needs a `PENDING` value in `memberships.status`, whose CHECK constraint is `('ACTIVE','REVOKED')`. Technically a forward-only ALTER, but it would create a state with **no exit**: no accept capability is in Phase 1's six slices, and `ResolveStoreAccessService`/`ResolveOrganizationAccessService` both require `isActive`, so every PENDING member would be permanently denied. A dead state that nothing can leave is worse than an honest limitation; (C) add an existing platform user directly as an ACTIVE member holding no roles.
  - **Decision: C.** It is the only reading the Phase 1 schema can express without creating a table the brief forbids or a state nothing can leave. `03` §167's ordering independently confirms the role split: invite creates the membership, `membership.role.assign` (slice 3) grants the roles, so a freshly invited member can do nothing until slice 3 runs. A test pins that (`membership_roles` is empty after an invite).
  - **Known consequence, deliberately accepted:** "invite" is a slight misnomer for what ships — nobody is asked, they are added. When the notification module lands (`01` §483 makes invitation a V1 flow) this capability likely needs the pending state and an accept flow after all, and that will be a **contract change**, not an additive one. Flagged here so it is a decision then rather than a surprise.

**2. The invitee is identified by email, which reveals whether an address has an account.** A caller with `membership.invite` gets `RESOURCE_NOT_FOUND` for an unknown address and `CONFLICT`/`201` for a known one.
  - Options: (A) take a `userId` instead — no enumeration, but unusable: an admin does not know a stranger's UUID; (B) always return success and silently do nothing for an unknown address — the usual mitigation, but it depends on a pending state to be honest, and (1) established there isn't one, so it would be a lie rather than a deferral; (C) accept email and return the real outcome.
  - **Decision: C**, with the exposure noted rather than hidden. It is narrow: the caller must already hold an active membership *and* a role granting `membership.invite` (owner or admin) in a specific organization, so this is not an unauthenticated oracle. Revisit together with (1) when the accept flow exists — a pending state makes (B) truthful and is the right time to adopt it.

**3. Re-inviting a REVOKED member returns CONFLICT rather than reactivating.** `UNIQUE (tenant_id, user_id)` makes the row collide regardless of status.
  - **Decision:** leave it as `CONFLICT`. No capability can currently produce a REVOKED membership — `membership.revoke` is not one of the six slices; it is the outstanding Phase 1 exit criterion — so the state is unreachable in practice today. Reactivation semantics belong with `membership.revoke`, which is where the question actually arises, and deciding them now would be inventing a rule for a state nothing can create.

**Also settled, minor:** the invitee's account status is not checked. A SUSPENDED user cannot authenticate (`ValidateSessionService` rejects them), so the membership row grants nothing; refusing here would duplicate that rule in a second place and need an error code §7 does not define for it. — Duplicate detection uses the unique index rather than a `SELECT` pre-check: unlike `organization.create` a pre-check *would* be visible under RLS here, but it would still be wrong under concurrency. — The audit event carries the invitee's address in `metadata`, because `resource_id` is a membership id that, on the failure path, names a row that was never written; without the address a FAILURE row cannot say who the attempt concerned.

**Status:** RESOLVED for Phase 1. Items 1 and 2 are **OPEN for V1** and must be revisited together when the notification module and an accept flow exist.

## 2026-08-23 — `organization.create`: five decisions the docs pack leaves open

**Context:** implementing Task 2 slice 1 (`08_PHASE_1_BRIEF.md` §3). The capability is one row in `05_API_CAPABILITY_CONTRACTS.md` §4.1 (`organization.create | user | MEDIUM_WRITE | yes`) plus one constraint in `04_DATABASE_BLUEPRINT.md` §5 ("organization slug unique within its namespace"). Nothing else in the pack describes its behaviour, and it is the first capability that does not fit the golden path's shape exactly, because it *creates* the tenant rather than acting inside one.

**1. Does creating an organization also make the creator a member?** The pack never says. `membership.invite` is a separate slice (§3 item 2) and `organization.switch` is another (item 6).
  - Options: (A) create only the organization — but every subsequent capability authorizes through `membership_roles` (pipeline step 6), so the organization would be permanently unreachable by anybody, including its creator, and slices 2 and 6 would have no reachable starting state; (B) create the organization, an ACTIVE membership for the creator, and grant them the platform `owner` role, all in one transaction.
  - **Decision: B.** This resolves an ambiguity rather than inventing architecture: (A) makes the documented slice order impossible to execute, so it cannot be the intended reading. The role granted is `owner` from the existing platform catalog — no new role, no new permission. Cross-module write goes through a new `RoleGrantRepository` port exported from `modules/authorization/contracts/`, mirroring how `modules/audit` already exposes `createAuditEventRepository`; `modules/tenant` never touches `membership_roles` directly.

**2. Pipeline steps 2–4 have nothing to resolve.** The golden path puts "resolve membership, check resource access, build `TenantContext`" in `StoreAccessGuard`, before any transaction. Here there is no pre-existing membership and no resource to check access to.
  - Options: (A) add a guard anyway, whose only acts are validating the body and calling `randomUUID()`; (B) do that work in the controller and document the absence.
  - **Decision: B.** A guard named for access resolution that resolves no access would imply a check that did not happen — worse than an honest gap. What genuinely survives of those steps is input validation and minting the organization id, which is also the tenant id and therefore has to exist *before* the transaction, because it is what the RLS context is set to. `AGENTS.md` §2 requires documenting a mismatch rather than inventing a second structure; this is that record. Everything else — step 1 in a guard, one `withTenantContext` transaction for step 7, one durable audit event for the whole attempt — is the golden path unchanged.

**3. Pipeline step 6 has no permission to assert.** §4.1 scopes the capability to `user`, and the caller holds no membership until step 7 creates one, so `membership_roles` has nothing to read.
  - **Decision:** `requiredPermissions: []`, and the controller *throws* if that list is ever non-empty, rather than looping over it and silently doing nothing. An unenforceable requirement that looks enforced is the failure mode ADR-030 exists to prevent.

**4. Idempotency: §4.1 says yes, and there is no mechanism.** ADR-009's shared idempotency store is Phase 2, no idempotency table is in `08` §4's scope list, and `AGENTS.md` §4 forbids a module-local substitute.
  - Options: (A) `idempotent: true` in the capability definition, matching §4.1 — but the ADR-033 generator turns that metadata into a published contract, so the OpenAPI document would advertise an `Idempotency-Key` guarantee nothing provides; (B) `idempotent: false`, recording what is actually enforced.
  - **Decision: B**, with the divergence stated in the capability file. The globally-unique slug index means a naive retry returns `CONFLICT` rather than creating a second organization, so the failure mode is a wrong status code on retry, not duplicate data. **Flip to `true` in the slice that lands ADR-009.**

**5. Duplicate-slug detection cannot be a pre-check.** Inside the transaction `app.tenant_id` is the *new* organization's id, so a `SELECT` for a colliding slug owned by another tenant returns zero rows — RLS hides exactly the row the check is looking for.
  - **Decision:** no pre-check exists. `OrganizationRepositoryPg` catches the `organizations_slug_key` unique violation and raises the domain-level `OrganizationSlugTakenError`, which `CreateOrganizationService` maps to the documented `CONFLICT` code. The unique index is both the only authority that sees the whole namespace and the only race-free one. `platform/db/constraint-violation.ts` inspects the error structurally rather than importing `pg`, which ADR-030 confines to three platform files.

**Also settled, minor:** `reserved_subdomains` is deliberately not consulted — `08` §5 and `04` §5 both scope that rejection to *store* slug creation, and the table belongs to the `store.create` slice. Organization slugs are still constrained to a DNS-label-safe character set (3–63 chars, lowercase alphanumeric segments separated by single hyphens) so nothing has to be re-validated under ADR-028 later.

**Status:** RESOLVED, except item 4, which is **OPEN pending ADR-009** (Phase 2).

## 2026-08-22 — `modules/money`: four decisions ADR-022 leaves to the implementer

**Context:** implementing Phase 1 step 4 (`06_IMPLEMENTATION_PLAN.md`: currency registry + `Money` + allocator). `03_TECHNICAL_BLUEPRINT.md` §2 already assigns this to a `money/` module ("Money value object, currency registry, allocator"), so module ownership was not in question. ADR-022 is precise about representation, float prohibition, per-currency minor units, allocation and cross-currency arithmetic, but silent on four points that had to be settled to write the code.

**1. Which currencies to seed.** ADR-022 requires a currency table but names no rows.
  - Options: (A) seed nothing, let each deployment populate it — leaves the ADR-022 verification item "a currency with zero minor units round-trips" with no data to run against; (B) seed a broad ISO 4217 set (~180 rows) — bulk reference data nothing yet consumes; (C) seed a small set chosen to span the minor-unit exponents that actually break assumptions.
  - **Decision: C.** Seeded `IRR` (0), `USD` (2), `EUR` (2), `JPY` (0), `KWD` (3). The spread is the point: 0 and 3 both exist, so no caller can pass its tests while assuming 2. `IRR` additionally carries the presentation pair (`IRT`, divisor 10) because rial-stored/toman-displayed is the platform's home-market case per ADR-023, and that factor of 10 must never appear as a literal in code. Widening to the full ISO list is a data task, not a design change, whenever a deployment needs it.

**2. Where the presentation unit lives.** ADR-022 item 4 says the presentation unit, divisor and symbol are configuration and that "Domain and Application never see a presentation unit," but does not say how that is enforced.
  - **Decision:** the columns exist on `currencies` (configuration has exactly one home), and the domain `Currency` entity deliberately does **not** carry them — `CurrencyRepositoryPg` selects only `code`, `name`, `minor_units`. The rule is structural rather than a convention: domain code cannot reach a presentation unit because the object it holds has no such field. A test pins the entity's key set so a future field addition fails loudly. Applying the divisor is interface-layer work and is deferred until something actually renders money; nothing does yet.

**3. What `Money` carries.** ADR-022 item 1's type is `{ amountMinor: bigint; currency: string }`, but the DTO in item 7 also needs `minorUnits`, which suggests carrying the `Currency` entity instead of a bare code.
  - **Decision:** follow item 1 literally — `Money` holds `amountMinor: bigint` + `currency: string`. Allocation and all arithmetic operate purely on integer minor units and never need the exponent, so carrying it would add a registry dependency to a value object that does not use it. The exponent is supplied at the boundary instead: `toMoneyDto(money, currency)` takes the `Currency` explicitly and throws if it does not match. This keeps the registry lookup at the edge, where it belongs, and makes "which currency's exponent is this?" an explicit argument rather than an assumption.

**4. Rounding modes and decimal multiplication.** ADR-022 item 5 requires every fraction-producing operation to declare a rounding mode, default half-up.
  - **Decision:** implement no fraction-producing operation at all in Phase 1. `multiply` takes a `bigint` and is exact; splitting by a ratio goes through `allocate`, which distributes the remainder rather than rounding each part independently — which is what item 5 mandates for allocation anyway. So there is currently no operation that needs to declare a mode, and no `RoundingMode` enum has been invented ahead of a caller. The first capability that genuinely needs a decimal factor (ADR-025 proration is the likely one) adds it then, with its mode declared at that call site.

**Also settled, minor:** `modules/money`'s domain errors (`CurrencyMismatchError`, `InvalidCurrencyCodeError`, `InvalidAllocationError`) are plain `Error` subclasses, not `CapabilityError`. `CapabilityError` carries an `httpStatus`, which is an interface concern, and `Money` has no HTTP surface; a caller maps these at its own boundary like any other domain failure.

**Module shape:** `contracts/`, `domain/`, `infrastructure/` and `migrations/` are populated. `application/` and `interfaces/` are **not** — there is no use case and no HTTP surface in this slice, and creating an empty service or controller to fill the template would be exactly the premature abstraction `AGENTS.md` §4 warns against. `03_TECHNICAL_BLUEPRINT.md` §2's "each module owns interfaces/, application/, domain/, infrastructure/, and contracts/ where other modules must consume it" is read as naming the permitted layers, not as requiring every one to be occupied before it has content. The first Phase 2 slice that resolves a currency through a use case adds `application/`.

**Status:** RESOLVED.

## 2026-08-22 — Pipeline step 6 must share the transaction with steps 7–8 (fixed); NestJS guards were the wrong home for it

**Context:** raised in review. `08_PHASE_1_BRIEF.md` §2 orders the golden path: …4. build TenantContext → **5. transaction open + RLS context** → 6. permission authorization → 7. application service execution → 8. audit event. `03_TECHNICAL_BLUEPRINT.md` §3.1 states the same chain linearly (`Open Transaction + set RLS session context → Validate Input → Authorize Permission → … → Execute Application Service → Commit Domain Data + Outbox → Audit`). Both put authorization *after* the transaction opens, therefore inside it, together with execution.

**What was actually built (the defect):** three separate transactions. `StoreAccessGuard` opened one (steps 2–3), `PermissionGuard` opened a second (step 6), and `StoreController` opened a third (steps 7–8). Each committed before the next began.

**Was it an RLS bypass?** No — and the review's precise question deserves a precise answer. `StoreAccessGuard` read `store_memberships` over the `appDb` connection (the `nexora_app` role: `NOSUPERUSER`, `NOBYPASSRLS`, not the tables' owner, with `FORCE ROW LEVEL SECURITY` on), *inside* `withTenantContext()`, with `app.user_id` set and `app.tenant_id`/`app.store_id` empty. RLS was enabled and evaluated for that read; it matched via the self-access clause (see the entry below), not by evading a policy. So: not a bypass, but genuinely the wrong transaction boundary.

**Why the boundary still mattered.** Splitting step 6 from steps 7–8 makes the permission check a check against state that has already been committed and released: between `PermissionGuard`'s commit and the controller's transaction, a concurrent `membership.role.assign`/revoke could change the answer, and the read would proceed on a stale authorization. Same argument for the audit row: an audit written in a transaction that can commit independently of the read it describes is not an audit of that read.

**Fix (implemented):** `PermissionGuard` and its `@RequirePermission` decorator are deleted. `StoreController` now opens exactly one transaction via the single helper and runs step 6 (permission), step 7 (execute), step 8 (audit) inside it. Guards are reduced to steps 1–4, which the brief deliberately places *before* step 5 — they establish which tenant may be trusted, so they cannot already be running inside that tenant's context. The required permission is no longer a string literal at the route: it comes from `modules/tenant/interfaces/store-read.capability.ts`, the `<capability>.capability.ts` file `03_TECHNICAL_BLUEPRINT.md` §2.1 asks for.
**Status:** RESOLVED.

## 2026-08-22 — Conflict: is the audit event inside the transaction (08 §2) or after commit (03 §3.1)?

**Context:** found while making the fix above. The two normative documents disagree on where step 8 sits. `08_PHASE_1_BRIEF.md` §2 lists `5. transaction open … 7. execute … 8. audit event`, which reads as all-inside-one-transaction. `03_TECHNICAL_BLUEPRINT.md` §3.1 spells the chain out as `… Execute Application Service → **Commit Domain Data + Outbox** → Audit → Return Stable Result`, placing audit explicitly *after* the commit. Precedence (`README_START_HERE.md`) puts the ADR index above both and does not settle this; `03` and `08` are peers in the read order.

This is not academic. `ReadStoreService` writes a `FAILURE` audit row and then throws `RESOURCE_NOT_FOUND`. Inside one transaction, that throw rolls the audit row back — so the failure audit never persists, which contradicts `08_PHASE_1_BRIEF.md` §6's exit criterion "every capability in scope emits an audit event". Audit-after-commit (03's reading) does not have this problem; audit-inside-transaction (08's reading) gives atomicity between the domain effect and its audit record but silently loses every failure audit.

**Current state:** audit is inside the transaction (08's reading), because that is what the fix above produced and because for `store.read` specifically the `!store` branch is **currently unreachable** — `StoreAccessGuard` requires a `store_memberships` row, whose `store_id` is a foreign key to `stores(id)`, so a store the caller has access to cannot fail to exist. The defect is therefore latent here, but it becomes live the moment any capability audits a failure it also throws on — i.e. almost immediately in Task 2 (`store.create` on a reserved slug, `membership.invite` on a duplicate).
**The three options:**
  - **(A) Inside the transaction**, as `08_PHASE_1_BRIEF.md` §2 reads. Audit is atomic with the domain effect — an audited read cannot appear without the read having happened, and vice versa. Cost: an audit row written before a throw is rolled back by that throw, so failure audits are lost unless failure auditing moves elsewhere entirely.
  - **(B) Before commit, but on a separate connection/transaction that commits independently** — the same shape as an idempotency claim, which must also survive the outcome of the work it guards. Audit is written at the point in the pipeline the brief specifies (step 8, before the domain transaction resolves), yet persists whether that transaction commits or rolls back. Cost: the audit row and the domain effect are no longer atomic with each other — a crash between the two can leave an audit row describing a rolled-back effect, so audit means "this was attempted and authorized," not "this committed."
  - **(C) After commit**, as `03_TECHNICAL_BLUEPRINT.md` §3.1 reads. Failure audits survive, ordering matches `03` literally. Cost: an audit write that fails after a successful commit leaves a committed effect with no audit record at all — the worst failure mode of the three for an audit trail.

**Decision (2026-08-22):** **(B) is the target.** It is the only option where the audit record survives both outcomes *and* the operation cannot commit un-audited, and it reuses a pattern the platform already needs for idempotency (ADR-009), so it is one mechanism rather than two. The semantic shift it implies — an audit event attests to an authorized attempt, not to a committed effect — is accepted deliberately, and the outcome column (`SUCCESS`/`FAILURE`) is what distinguishes them.

**Superseded 2026-08-22: (B) is now implemented, not deferred.** An independent audit of commit `944e359` found this decision recorded but not built — `store.read` still audited inside its domain transaction, so a `FORBIDDEN` outcome (step 6 failing, before `ReadStoreService`/step 7 is even constructed) was **invisible to the only code that wrote audit events**, not merely "latent because unreachable" as reasoned above. That reasoning covered the `RESOURCE_NOT_FOUND` branch correctly but missed that permission denial is a *second*, independently reachable failure path with no audit coverage at all.

**Implementation:**
- `platform/db/connections.ts` adds a second pool, `AUDIT_DB`, distinct from `APP_DB`. `modules/audit/contracts/audit.contract.ts` exports `recordAuditEventDurable(db, context, event)`, which opens its own `withTenantContext()` transaction on whatever `db` it's given and returns once that commits — a self-contained "write one event durably" primitive.

**Correction to the above during implementation:** the domain transaction (`APP_DB`) and the audit write both had to complete before the controller decides what to return, but they cannot be nested inside a single `withTenantContext` callback and still be "independent" in the way that matters — the audit write must survive even if something *inside* the domain callback throws. The `RESOURCE_NOT_FOUND` branch remains genuinely unreachable through the HTTP path (confirmed by attempting to seed around it, which fails on `store_memberships`' foreign key to `stores`, not on any test assertion) and is covered only at the unit level (`read-store.service.spec.ts`).

## 2026-08-22 — How repositories participate in a `withTenantContext` transaction without domain seeing Kysely

**Context:** domain repository interfaces must not reference Kysely types (`FORBIDDEN-IMPORT-DOMAIN` explicitly forbids importing the query builder), but a repository call issued partway through `store.read`'s pipeline must run *inside* the one transaction `withTenantContext()` opened, using its `trx`, not a fresh connection — otherwise RLS session variables set on `trx` don't apply to the query. Full NestJS request-scoped DI (or AsyncLocalStorage-based ambient transaction propagation) would solve this generically but is real infrastructure complexity with nothing yet to generalize from — exactly the premature abstraction `AGENTS.md` warns against for a single slice.
**Decision:** repository interfaces (`domain/*.repository.ts`) stay connection-agnostic (`findById(id): Promise<User | null>`, no connection parameter — keeps domain pure). Concrete implementations (`infrastructure/*.repository.pg.ts`) take the Kysely connection (`Kysely<Database>` for RLS-exempt tables, or the `Transaction<Database>` from inside a `withTenantContext` callback for tenant-scoped ones) as a **constructor** argument. The `interfaces/` layer (guards, controllers) is the composition root: it constructs the concrete repository bound to the right connection and passes it into the application service's constructor. This is allowed because `DEP-DIRECTION-APPLICATION` forbids *application* importing infrastructure, but says nothing about `interfaces` doing so — `interfaces` importing `infrastructure` to wire things together is exactly what a composition root does. Application services themselves import only domain repository interfaces + contracts, never a concrete implementation, so they stay swappable and testable with a fake.
**Status:** RESOLVED. Revisit if/when a second capability needs to share a transaction across more than one guard+controller boundary — that's the point at which a generic ambient-transaction mechanism starts paying for itself.

**Extension — cross-module writes inside the same transaction (audit):** `store.read`'s step 8 (audit event) must write to `modules/audit`'s table using the *same* transaction as step 7's read, for atomicity — but `DEP-DIRECTION-CROSS-MODULE` forbids `modules/tenant` importing `modules/audit`'s `infrastructure/` directly, only its `contracts/`. Resolution: `modules/audit/contracts/index.ts` exports a **factory function**, `createAuditEventRepository(conn: Kysely<Database> | Transaction<Database>): AuditEventRepository` — the one place a module's `contracts/` intentionally imports Kysely types, specifically so a caller can hand in the `trx` it already has without ever importing `audit`'s concrete PG class. Every module that needs to write audit events from inside its own transaction uses this same factory; it is not re-invented per module.

## 2026-08-22 — NestJS's type-based constructor DI silently fails under esbuild/tsx — never rely on it

**Context:** `modules/authorization/interfaces/permission.guard.ts` originally took `Reflector` as a constructor-injected dependency (`constructor(private readonly reflector: Reflector) {}`), NestJS's normal idiom. At runtime, `this.reflector` was `undefined`, throwing `TypeError: Cannot read properties of undefined (reading 'get')` on every request through `PermissionGuard`. Root cause: NestJS's DI resolves an implicitly-typed constructor parameter (no `@Inject(TOKEN)`) by reading TypeScript's `emitDecoratorMetadata`-generated `design:paramtypes` array via `reflect-metadata` — and **esbuild does not implement `emitDecoratorMetadata`** (it only supports the legacy decorator *syntax*, not this metadata emission). This repo runs everything through `tsx`/Vitest, both esbuild-based, so any class relying on implicit type-based constructor injection gets `undefined` for that parameter with no compile-time warning — `tsc --noEmit` type-checks fine because the *types* are correct; only the *runtime* metadata is missing.
**Decision:** don't rely on NestJS's DI container for constructor injection by implicit type anywhere in this codebase, echoing (not contradicting) the earlier choice to keep repositories/services explicitly composed rather than DI-managed. Concretely: `Reflector` is instantiated directly (`private readonly reflector = new Reflector()`) since it has no dependencies of its own; the same "construct it directly, don't ask the container" approach already used for every repository and application service extends naturally to any NestJS-provided utility class a guard/controller needs. `@Injectable()`/`@Controller()`/`@Get()`/`@UseGuards()`/`SetMetadata()` etc. — decorators that don't depend on constructor parameter *type* metadata — are unaffected and safe to keep using.
**Status:** RESOLVED. If a future slice genuinely needs the DI container (e.g. request-scoped providers), either switch the run/build step off esbuild for that path or use explicit `@Inject(TOKEN)` tokens everywhere (which don't need `emitDecoratorMetadata`) rather than implicit type inference.

## 2026-08-22 — `INSERT ... RETURNING` re-checks the `USING` policy, not just `WITH CHECK` — breaks naive organization creation under FORCE RLS

**Context:** found while writing `apps/api/test-support/seed.ts`'s `seedOrganization()`, which needs to hand the caller the new organization's id. `organizations`' RLS policy is `USING (tenant_id::text = current_setting('app.tenant_id', true)) WITH CHECK (true)` (the `WITH CHECK (true)` from the entry below, specifically to let organization creation happen with no pre-existing tenant to check against). Verified empirically (`psql`, both as `nexora_app` and as `nexora_migrate`, the table owner — same failure either way, so this is not a role/grant issue): a plain `INSERT ... VALUES (...)` succeeds, but the identical insert with `RETURNING id, tenant_id` fails with "new row violates row-level security policy," even though `WITH CHECK` is unconditionally `true`. Postgres applies the table's `USING` policy (not `WITH CHECK`) to rows an `INSERT`/`UPDATE` returns, since returning a row is treated as a read of it — and a brand-new organization's `tenant_id` (generated from its own not-yet-trusted `id`) can never match whatever `app.tenant_id` happens to be set to.
**Options considered:** (A) set `app.tenant_id` to the new row's id *before* inserting, which only works if the id is already known — i.e. generated client-side, not by the column's `DEFAULT gen_random_uuid()`; verified this combination (client-generated id + `set_config` first + `RETURNING`) succeeds. (B) Generate the id client-side and skip `RETURNING` entirely, since the caller already knows the id; verified this succeeds with no `set_config` needed at all, because with no `RETURNING` only `WITH CHECK` is evaluated. (C) Relax `organizations`' `USING` clause to also allow self-access analogous to `memberships`/`store_memberships` — rejected, there is no independent identifier to key that off (the row *is* the tenant).
**Decision:** B — simplest, no context-setting choreography needed. `seedOrganization()` generates the id with `randomUUID()` and inserts without `.returning()`. **This is the pattern Task 2's real `organization.create` capability must also use** — noted here so it doesn't have to be rediscovered.
**Status:** RESOLVED for Task 1's test seeding. Flag for Task 2: `organization.create`'s application service must generate the id itself, not rely on the column default + `RETURNING`.

## 2026-08-22 — No cross-module foreign-key constraints; `organizations.tenant_id` is a generated mirror of `id`

**Context:** two schema-design questions that came up writing Task 1's actual migrations, both direct corollaries of already-stated rules rather than new ambiguity, recorded because they set the pattern every later migration copies.

1. **Cross-module FKs.** `04_DATABASE_BLUEPRINT.md` §1: "every table has exactly one owning module. Cross-module reads go through contracts, never through a foreign repository." A `REFERENCES` constraint from e.g. `modules/tenant/.../memberships` to `modules/identity/.../users` is the schema-level version of exactly that coupling, and also creates a real migration-ordering hazard (`platform/db/discover-migrations.ts` sorts `<filename>__<module>` alphabetically by module, so `identity`'s migrations don't reliably run before `tenant`'s). **Decision:** FK constraints only within the same module's own tables; a cross-module reference (e.g. `memberships.user_id`, `store_memberships.user_id`, `membership_roles.tenant_id`/`membership_id`, `audit_events.tenant_id`/`actor_user_id`) is a plain indexed column, integrity enforced at the application layer via the owning module's contract.
2. **`organizations.tenant_id`.** An organization *is* the tenant — there is no separate tenant row for it to point at, so a literal `tenant_id` column referencing itself would be redundant and error-prone to keep in sync by hand. **Decision:** `tenant_id uuid GENERATED ALWAYS AS (id) STORED` — always consistent by construction, and it means `tools/conformance/rules/schema.ts`/`schema-live.ts` need no special case for `organizations`: it has a real `tenant_id` column and a normal `tenant_id = ...` RLS policy like every other table.

**Status:** RESOLVED.

## 2026-08-22 — RLS bootstrap: how a query resolves tenant context before tenant context exists

**Context:** `08_PHASE_1_BRIEF.md` §2 steps 2–3 (resolve organization membership, check store access) must query `memberships` and `store_memberships` — both tenant-owned, RLS-protected tables — *before* step 4 builds the trusted `TenantContext` those tables' RLS policies would normally require. **Decision:** `04_DATABASE_BLUEPRINT.md` §6 already sets three session variables, not one — `app.tenant_id`, `app.user_id`, `app.store_id` — which only makes sense if some policies key off `app.user_id` alone. `memberships` and `store_memberships` get a policy allowing a row when **either** `tenant_id = current_setting('app.tenant_id', true)` **or** `user_id = current_setting('app.user_id', true)`, so a user can always see their own membership rows (self-access, used to bootstrap which tenant to trust) even with no tenant context set, while a fully-scoped query (e.g. "list every member of org X") still requires `app.tenant_id`. `platform/db/tenant-context.ts`'s `withTenantContext()` is generalized from a single `tenantId` argument to a `{ tenantId, userId, storeId }` context object (all independently nullable) so it can express both the bootstrap phase (`userId` set, `tenantId`/`storeId` null) and the fully-trusted phase (all three set) through the one helper — no second helper, no duplicate transaction-opening code.
**DECIDED 2026-08-22: option (A) — the self-access clause stays**, on the stated grounds that removing it disables the system. It remains on `memberships` and `store_memberships` only (`user_id = current_setting('app.user_id', true)` OR the tenant match), and must not be copied onto other tenant-owned tables without a decision of its own: it is a deliberate, narrow bootstrap affordance for the two tables read at pipeline steps 2–3, not a general pattern. Tracked as a standing risk in `RISK_REGISTER.md` R-003, which Task 2 re-evaluates against a clause-free alternative.

**Superseded status record (kept for history):** **OPEN — flagged 2026-08-22, still implemented (unlike the two entries above), see below.** This is the same class of decision as the two RLS entries now reverted: it widens a tenant-owned table's policy beyond a plain `tenant_id` match, which §5 does not describe. It is surfaced here for the same decision-maker rather than left marked RESOLVED on my authority.

It is *not* backed out the way the other two were, because it is load-bearing in a way they are not: `memberships` and `store_memberships` are read at pipeline steps 2–3, which by the brief's own ordering run *before* step 5 opens the tenant transaction. With a plain `tenant_id`-only policy those two reads return zero rows, the store access check can never succeed, and `store.read` returns `STORE_ACCESS_DENIED` for every request — i.e. removing it does not leave a more-conformant system, it leaves a non-functional one. Backing it out therefore needs a replacement design in the same change, which is a decision, not a revert.

Options if the self-access clause is not acceptable:
  - **(A)** keep it (current state) — a user may always read their own membership rows regardless of tenant context; cross-user reads still require `app.tenant_id`.
  - **(B)** resolve steps 2–3 through a `SECURITY DEFINER` function that encapsulates exactly the bootstrap lookup, keeping the table policy strict. Narrower blast radius, but moves trust into a database function.
  - **(C)** give the session row an authoritative `tenant_id` (see the `sessions` entry above — these two questions are coupled) so `app.tenant_id` is known from step 1 and the bootstrap phase disappears entirely. Most structurally clean; largest change; depends on how the `sessions` question is decided.

Note (A)/(B)/(C) interact with the `sessions` decision — worth deciding both together.

## 2026-08-22 — RLS: FORCE ROW LEVEL SECURITY or a non-owner app role

**Context:** while writing `platform/db/tenant-context.spec.ts` to prove the new Kysely-based `withTenantContext()` helper against real PostgreSQL, empirically verified (via `psql`, see session transcript) that **the role owning a table bypasses `ENABLE ROW LEVEL SECURITY` entirely by default** — a table owner sees every tenant's rows regardless of `app.tenant_id`, `ENABLE ROW LEVEL SECURITY` notwithstanding. This is standard PostgreSQL behavior (RLS never applies to a table's owner or a superuser unless forced), but it directly threatens `08_PHASE_1_BRIEF.md` §5's non-negotiable rule: "the application database role cannot bypass RLS." This Phase 0 scaffold currently uses one role (`nexora`) for everything — the migration runner creates tables as `nexora`, so `nexora` owns them, so `nexora` would silently bypass RLS if it's also the role the running application connects as.
**Options considered:**
  A. `ALTER TABLE ... FORCE ROW LEVEL SECURITY` on every tenant-owned table (in addition to `ENABLE ROW LEVEL SECURITY`) — makes RLS apply even to the owner. Confirmed working empirically (with FORCE, the owner is correctly restricted to zero rows with no tenant context, and an INSERT with the wrong/no tenant context is rejected by the policy's implicit `WITH CHECK`).
  B. Two roles: a migration/owner role (used only by the migration runner, never by the running application) and a separate, non-owner application role granted `SELECT`/`INSERT`/`UPDATE`/`DELETE` via `GRANT` — RLS applies automatically to any non-owner role without needing `FORCE`. This is the more conventional production pattern and also limits the app role's privileges (can't `DROP TABLE`, alter schema, etc. — useful defense in depth independent of RLS).
  C. Both — `FORCE` as a belt-and-suspenders default even with a separate app role, in case a future migration accidentally reuses the owner role for a live connection.
**Decision, confirmed by the user 2026-08-22: C — both, plus a runtime assertion.** Not belt-and-suspenders as a hedge; three independent, mandatory layers, none optional:

1. **Two roles.** `nexora_migrate` owns the schema and runs migrations only (`platform/db/migrate-cli.ts`, and the harness's live-DB schema-structure checks — see `platform/config.ts`'s `loadMigrateDbConfig()`). `nexora_app` (`NOSUPERUSER NOBYPASSRLS`, never an owner) is the only role the running app, and its tests, connect through (`loadDbConfig()` / `loadConformanceTestDbConfig()`). Bootstrapped by `platform/db/init/001_roles.sql` (mounted into `docker-entrypoint-initdb.d/` by `docker-compose.yml`), including `ALTER DEFAULT PRIVILEGES FOR ROLE nexora_migrate ... GRANT ... TO nexora_app` so every future table nexora_migrate creates automatically grants nexora_app DML rights — no per-migration `GRANT` needed. Verified locally against the native PostgreSQL 17 install (same statements, by hand).
2. **`FORCE ROW LEVEL SECURITY` on every tenant-owned table, mechanically enforced.** Added as a new conformance rule, `SCHEMA-MISSING-FORCE-RLS`, in both `tools/conformance/rules/schema.ts` (static) and `schema-live.ts` (live introspection via `pg_class.relforcerowsecurity`) — checked only once `ENABLE ROW LEVEL SECURITY` + a policy already exist, so it doesn't pile onto `SCHEMA-MISSING-RLS`'s message when RLS is absent outright. New fixture `tools/conformance/fixtures/schema-missing-force-rls/`, two new self-test cases (static + live), both passing. The `clean` control fixture was updated to include `FORCE` so it still asserts zero violations.
3. **A runtime safety assertion**, `platform/db/assert-role-safety.ts`'s `assertRoleCannotBypassRls(db, tableName)`: checks the connected role is not a superuser, does not have `BYPASSRLS`, and does not own the table being tested — throws a specific, actionable error naming which condition failed if any do. Called from `platform/db/tenant-context.spec.ts`'s `beforeAll`, before any test that asserts tenant isolation, per the user's own framing: "otherwise tenant-isolation tests would go green for the wrong reason." Verified this actually fires: manually pointed `DATABASE_URL` at `nexora_migrate` (the owner) and separately at the `postgres` superuser — both failed loudly with the expected message and skipped the isolation assertions rather than passing vacuously.

`platform/db/tenant-context.spec.ts` now does schema DDL via a `nexora_migrate`-backed Kysely instance and every tenant-scoped query via a `nexora_app`-backed one through `withTenantContext()` — mirroring how migrations vs. app queries will work in Task 1.
**Status:** RESOLVED.
