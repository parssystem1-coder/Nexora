## 2026-09-03 — ADR-039 and ADR-040 ruled. No ADR in this repository is open.

**Context:** ADR-039 and ADR-040 were the last two `OPEN` ADRs. Neither blocked a Phase 2 migration, which is exactly why they survived a programme that closed nineteen others — and both became expensive at the same moment, the first deployment carrying real traffic or running a second instance. **After this commit the index has no `OPEN` ADR**, which is the condition this programme has been working toward since 2026-08-28.

**ADR-039 also hid something that is not an operational nicety.** ADR-021 requires tenant isolation to work through a session setting on a pooled connection. **A pooled connection that carried one request's tenant context into the next checkout would be a cross-tenant read** — the same class of defect Session 9 found in partitioning, reached by a different route, and invisible to every existing isolation test because all of them set a context before they query.

**Options considered:** both rulings **follow the recommendations already recorded in their own ADRs** — A+D+E for ADR-039, A+D+F for ADR-040. Three judgements were this session's, and two of them corrected the session brief.

- **A number or a derivation.** A derivation. A pool size written as a constant is wrong the first time anything about the deployment changes.
- **Whether to adopt `pino`.** No. Void twice over — see below.
- **Whether the conformance rule could carry the logging boundary.** Half of it. See below.

**Decision:**

**ADR-039 — a derivation, not a number.** `pool_max = floor((max_connections − reserved) / (instances × pools_per_instance))`. **`pools_per_instance` is 2, not 1, and that is the part worth carrying**: `connections.ts` creates `APP_DB` and `AUDIT_DB` per process, so a derivation written per instance understates the draw by half — which is precisely how ADR-039's own `AUDIT_DB`-starvation constraint gets violated by someone who believed they had done the arithmetic. The application **refuses to start** when the configured product exceeds the budget, on ADR-023 item 1's shape, because an oversubscribed pool otherwise fails at the worst moment: under load, on some requests and not others. And **a larger pool is not a faster system** — recorded once so nobody "fixes" latency by raising it.

**Measured inputs, cited as what they are.** Native PostgreSQL 17.5 (Docker is not installed on this machine): `max_connections` 100, `superuser_reserved_connections` 3. The full local suite peaks at **23** concurrent connections at 7 Vitest workers and CI at **10** at 3 — the only real observation of this system's connection behaviour that exists, and **test-harness numbers rather than a production sizing input.** ADR-010's targets remain unverified assumptions by its own amendment, so they bound nothing either.

**The tenant-scope property was verified, not assumed — and it holds.** `platform/db/tenant-context.ts` calls `set_config('app.tenant_id', …, true)` inside `db.transaction().execute(...)`. The third argument is `is_local`, and it is **`true`**: the setting reverts at COMMIT. **There is no defect and nothing was changed.**

**It is now guarded, and that is the one piece of code this session added.** `platform/db/tenant-context-pool-reuse.spec.ts` runs a transaction under a tenant context, **proves the same backend is reused by comparing `pg_backend_pid()` and fails rather than passing vacuously if it is not**, then asserts the setting is gone and that a tenant-owned table returns **zero rows** on the recycled connection — with a row seeded that *was* visible inside the transaction, so the zero proves refusal rather than an empty table. A second test proves one tenant's context does not leak into the next transaction on the same backend.

**It was watched failing.** Flipping that third argument to `false` turns the file red at the leftover-setting assertion; reverting turns it green, with no residue. That is ADR-030's standard, and this property is a single argument away from silent breakage no type checker and no other test would catch.

**Conformance caught the first version of that test, and the rule won.** It constructed its own `pg.Pool` with `max: 1` to make reuse deterministic — and `DB-ACCESS-RAW-PG-IMPORT` confines `pg` to three platform files. **The test was rewritten to use `createDb` and assert the backend PID instead; no exception was added.** Reaching for an `exceptions.json` entry to make a test convenient is exactly what `CLAUDE.md`'s standing rule forbids, and the rewritten test is no weaker — it fails loudly if reuse ever stops happening.

**Four timeouts, each with the failure it prevents**, set server-side per role per the recommendation's option D. `statement_timeout` and `idle_in_transaction_session_timeout` on `nexora_app`; **`lock_timeout` on `nexora_migrate`**, because a migration queueing behind a long read then blocks every write behind *itself*, and under forward-only migrations that turns a slow deploy into an outage. A fourth — a request-scoped deadline shorter than the HTTP timeout — **is not in ADR-039's option list**, is application-side by nature and cannot be a role default. The first three are the same value in every environment; the fourth is not, being bounded by deployment topology.

**ADR-040 — the boundary first, and the library is a consequence.** Logging is a port: no `domain` or `application` file imports a logging library. Metrics and traces deferred on option D's trigger, so that adding them later is an adapter rather than a refactor.

**How much is actually enforced, checked rather than claimed — and this is where the honest answer is half.** `DOMAIN_FORBIDDEN` already carries `^@nestjs/`, and the logger this repository uses is NestJS's `Logger` from `@nestjs/common`, so **a domain file importing it already fails CI today.** A logging-library pattern was added to that list as depth, with a deliberately failing fixture proving it fires. **The application layer is a different matter: `imports.ts` has no forbidden-package list for it at all** — its only application-layer rule is dependency direction — so extending it is a new constant, a new branch, a new rule id and a new fixture. That is a rule mechanism, not a list entry, and the brief's own instruction was not to invent one in a documentation session. **Recorded as owed with a named trigger: the first slice that adds a logging call in an `application/` file.**

**A log line carries the same `correlationId` `audit_events` records for that attempt.** ADR-034 item 4 puts one audit row per capability attempt; **a log line and an audit row for the same attempt must be joinable**, or an incident is investigated twice from two half-views that disagree.

**The never-log list changed on 2026-09-03 and the ADR says why.** ADR-037 item 3 forbids writing a plaintext secret to the database *"by any code path"*, and that prohibition is extended to logs **explicitly, because ADR-037 does not mention them** — a log file is the other place secrets end up, with none of the database's access control. And **ADR-057 has just put کد ملی, a legal name, a postal address and a phone number into the platform: before that ADR there was no personal data here to protect, and there is now.** A national identifier in a log line survives every retention policy that applies to the database and none that applies to logs — ADR-053's session purge, ADR-020's tenant purge and ADR-041's windows all stop at the database boundary. **Enforcement is stated honestly as a review rule, not a checked one**: a secret in a log is a runtime value, not a source-text pattern, so `rules/secrets.ts` cannot see it. Claiming enforcement the project does not have would be worse than the gap, because it stops anyone looking for a real check.

**Levels are tied to the taxonomy that already exists:** an expected, contracted error is not logged at error level. `05` §7 already distinguishes retryable `CONCURRENCY_CONFLICT` from permanent `CONFLICT`, and neither is a system fault. **An error channel that fills with contracted outcomes is an error channel nobody reads.**

**The `pino` recommendation is void twice over, and both reasons came from the repository.** **First, ADR-040's own option A — the recommended option — says the seam costs *"no dependency"***, so adopting `pino` would contradict the very option being ruled. **Second, a logger is already present and in use**: NestJS's `Logger` in `capability-attempt.ts` and `http-exception.filter.ts`, plus `logging.middleware.ts` emitting JSON through `console.log` — which is exactly the two-path situation ADR-040's option 1 describes, not a greenfield. **The ruling unifies onto the `LoggerService` seam NestJS already provides and adds no dependency**, with `pino` named as the candidate if a structured backend ever wants one. Nothing was installed.

**The brief was wrong about which risk row this is.** It directed the addendum at **R-039**, which is the `sessions`-growth row ruled by ADR-053 last week. **R-020 is the pooling row** — *"The PostgreSQL connection pool is entirely unconfigured"* — and its status cell still read *"decision not yet taken."* R-020 got the addendum.

**R-020 stays OPEN, and the reason is the distinction this register keeps making.** The decision is taken and the cross-tenant half is now *proven and guarded*. But `pool.ts` is still six lines with no `max`, and `001_roles.sql` still sets no timeout of any kind. **A ruling is a decision, not a configuration.** The row closes when the settings exist, at the deployment moment ADR-039's trigger names.

**Status:** **RESOLVED.** Both ADRs are ruled, both following their own recorded recommendations, and **no ADR in this repository is open** — 62 ADRs, 54 ACCEPTED, 8 DEFERRED, 0 OPEN. **What remains owed is implementation rather than decision**, which is a different kind of debt: the pool and timeout settings (R-020, at the first real deployment); the application-layer forbidden-package rule (ADR-040, at the first `application/` logging call); redaction at the logging seam; and the measurements ADR-039's revisit needs — peak concurrent checkouts, checkout wait time, and saturation frequency.

## 2026-09-03 — the serving bound that three documents referenced and none defined, and four domain rulings

**Context:** five findings about domains and the edge were unrecorded. Four are Phase 4. **One had a live hole in an existing release-blocking criterion:** ADR-024 item 9 calls a storefront that stays live after expiry *"a release-blocking defect"*, and its verification list required it to stop *"within the defined bound."* Documentation-only: no migration, no table, no feature code.

**The hole is worse than the session brief described, and the grep is the finding.** *"The defined bound"* is referenced in **three** places — ADR-019's own verification list (*"subscription expiry removes the storefront from serving within a defined bound"*), ADR-024's (*"storefront stops serving within the defined bound after expiry"*), and **`06_IMPLEMENTATION_PLAN.md`'s Phase 4 Exit criterion** (*"expiry stops the storefront within the defined bound"*) — **and no document defines it.** No `s-maxage`, `max-age` or TTL value appears anywhere in the pack. A release-blocking criterion with an undefined threshold cannot fail, so it cannot pass either, and a **phase exit** now turned on it.

**Options considered:** the rulings were the maintainer's. Three judgements were this session's, and two of them cut the session's own scope.

- **How much of Part D to record.** Much less than asked. **ADR-027 item 3 already rules apex routing** and already calls the apex target *"a long-lived public contract … an address the platform controls independently of any single hosting vendor."* The brief's Part D would have re-ruled it *and inverted its preference ordering* — item 3 makes the published address the baseline and `ALIAS` the improvement *"where the tenant's DNS provider offers it but is never assumed"*, while the brief made flattening preferred and the address a fallback. **Re-ruling a settled decision while appearing to add one is worse than adding nothing**, so the amendment adds only what item 3 does not say: the address must be an **edge** address, and **the origin accepts traffic only from the edge.**
- **Whether to open risk rows.** Neither candidate. Reasoning below.
- **Whether to settle ADR-027's certificate tension.** No — recorded, recommended, not ruled.

**Decision:**

**Part A — ADR-019 amended: two bounds, not one, and that is the substance.** The origin stops as soon as the data says so, bounded by the entitlement cache in front of ADR-024 item 2's derived function. **The edge is a different machine with a different clock, and nothing the origin does changes an object already in an edge cache.** Treating one bound as covering both is the error the amendment exists to prevent. **Origin: 60 seconds. Edge: 5 minutes.** Both recorded as **choices, not derivations**, so a later reader tunes them against measurement rather than re-deriving a rationale that was never there.

**The line that makes it enforceable rather than aspirational: no storefront response may carry an `s-maxage` greater than 300 seconds.** A purge is best-effort, and when it fails **the TTL is the only thing that holds** — so a promised bound *is* an upper limit on cache lifetime. That single rule turns *"we will invalidate the cache"* into something a test can check, and it is precisely the line a later performance change will be tempted to break.

**Purge is a declared port capability**, on ADR-023's discipline applied to ADR-019 item 4's existing CDN port: the port declares whether purge exists and whether it is by-URL, by-tag or whole-zone; code branches on the capability, never a vendor name; and **a provider that cannot purge is legal** — the edge bound is then the TTL alone, stated rather than silently degraded. **A failed purge is not allowed to be silent**, because persistent failure makes the promise unbounded rather than merely slow.

**`scheduled_job_runs` covers the purge outcome and no table was added** — §4 gives it *"job name, window, status, timings, error"*, confirmed. **One limitation stated rather than discovered later:** it holds **one row per job run, not one per purged object**, so whether per-domain purge outcomes need their own record is item 14's design question and neither the amendment nor the brief answers it.

**Part B — ADR-059.** 404 for a host that resolves to nothing (**ADR-028 item 3's, cited not re-decided**); **503 with `Retry-After`** while the subscription can still be revived; **410** once ADR-020's reversible window or ADR-024 item 6's reactivation window has closed; 404 for a missing path in a serving store.

**The important half is that the status is a projection of the lifecycle, not a switch.** A 503 is a promise the site is coming back, and held indefinitely it stops being true — an automated consumer that sees an unavailable site for weeks treats the URL as gone whatever the code says. So it is **computed by the same derived function ADR-024 item 2 already requires**; a second flag controlling the status would be exactly the second source of truth that rule forbids. **Two prohibitions**, both the standard way this gets done wrong: never a `200` with an "unavailable" body — a soft 404 that keeps the placeholder indexed as the store — and **never a redirect to a platform-branded page**, which moves a tenant's traffic and accumulated search signals onto the platform's own hostname; whatever the platform's interest in that, **it is not the platform's to take with a customer's domain.**

**What still answers while the store does not:** the **ACME HTTP-01 challenge path**, the **`HTTP_FILE` domain-verification path**, and nothing else. **`robots.txt` returns 503 with everything else, deliberately** — a crawler that cannot read it backs off rather than crawling, which is exactly right for a store that is temporarily dark, and asserting it in a test means a later "fix" has to argue.

**A tension in ADR-027 was surfaced and deliberately not settled**, and it is the part of the brief that turned out to need the most care. **Item 4** requires automatic renewal with **no** carve-out for a non-serving subscription; **item 10** says the certificate is *"left to expire naturally rather than being revoked."* *"Left to expire naturally"* reads as anticipating expiry, which implies renewal stops; item 4 implies it does not. **Neither is wrong alone and ADR-027 does not say which.** It matters: if renewal stops, a suspended tenant's certificate expires and their storefront shows a **browser interstitial instead of ADR-059's clean 503** — worse for a tenant about to pay, and unfixable by them. **ADR-059's rule is required under either reading** (renewal continuing needs HTTP-01 answerable now; renewal stopping needs it answerable at reactivation), so nothing is blocked by leaving it open. Recorded in both ADRs with a recommendation to settle it; **not ruled, because it is a decision and this session was not given it.**

**Part C — ADR-028 amended: a platform subdomain is never reissued to a different organization**, moving permanently into the reserved set on offboarding, returnable only to the same organization — which is what makes ADR-024 item 6's promise to restore *"the same store, domains and data"* keepable. **The cost is stated: the namespace only ever shrinks.**

**The amendment narrows item 8 visibly rather than quietly contradicting it**, and this is the catch that mattered most in Part C. **Item 8 says removal must *"free the hostname for a legitimate re-claim"*, and as written it covers platform subdomains too** — ADR-027 item 1's `type` enum includes `PLATFORM`. That is **correct for a customer-owned domain and wrong for a platform subdomain**, and the reason is the whole distinction: for a customer domain, **control of DNS *is* the ownership check** and it changed hands legitimately, which item 1's unique index and item 2's first-to-verify rule already handle; for a platform subdomain **nothing changed hands**, and only the platform can prevent the reissue. Everything else item 8 requires still applies to both.

**Part D — ADR-027 amended, narrowly.** The published address is an **edge** address, never an origin's: an origin address in thousands of zones is both an **unchangeable hosting decision** and a **directly attackable target that bypasses the edge for every tenant at once.** And **the origin accepts traffic only from the edge** — the requirement stated, the mechanism left to the `CdnProvider` port as item 6 already requires be verified per vendor and recorded in `PROVIDER_MATRIX.md`.

**No risk row was opened, and both judgements are recorded rather than assumed.**

**Subdomain reassignment: covered by R-004, which gained a dated addendum.** R-004 already records the **concurrent** form of exactly this mismatch — the store-slug namespace is per-organization while a subdomain namespace is global — and Part C's hazard is **the same mismatch across time.** Splitting them across two rows would let a future reader fix one and believe they had fixed both. R-004's own finding is untouched: the amendment rules **reissue**, not **collision**, and the concurrent case is exactly as open as it was.

**The published apex address: a design decision, not an open risk.** ADR-027 item 3 already ruled it a long-lived public contract, and the amendment adds the edge constraint. A hazard with an owned, specified control is not an open risk, and a row would restate the ADR without adding a trigger anyone would pull — the same judgement made for the wire unit in the previous entry.

**One implementability finding, recorded so Phase 4 does not meet it in a migration.** `reserved_subdomains` is a single `name text PRIMARY KEY` column, seeded with thirteen infrastructure names and **written by nothing at runtime** — every consumer only reads it. It **cannot express *"reserved because A released it, returnable to A"***, which Part C's ruling requires. **Applying ADR-056's test: it may wait** — the seeded rows are legitimately empty of any releasing organization, and the table carries no `REVOKE`, so a provenance column is a plain forward migration. **A Phase 4 implementation obligation, not a schema trap.**

**`PHASE_2_BRIEF.md` §9.12 carries only the Phase 2 half** — item 14's two bounds, the `s-maxage` ceiling and the purge-outcome recording. **§4 stays at 31 tables and §3 at sixteen capabilities**, said explicitly because a reader who sees purge outcomes discussed will look for a table. Everything else here is Phase 4 and was deliberately kept out of an already-open phase. `04_DATABASE_BLUEPRINT.md` §2.7 needed nothing: it sketches `store_domains` and `store_domain_certificates` conceptually and nothing in these rulings contradicts it — the provenance question belongs to `reserved_subdomains`, which §2.7 does not describe.

**Status:** **RESOLVED.** The undefined bound is defined ahead of item 14, which was the only deadline; the other four are recorded years before they are built, at the moment they cost nothing. **Owed and tracked:** ADR-027's renewal-during-non-serving tension (recommended, not ruled); `reserved_subdomains`' provenance column, at Phase 4; per-domain purge outcomes, item 14's design question; and R-004's concurrent slug-collision half, unchanged.

## 2026-09-03 — the unit a gateway speaks, and a direct-debit deferral with a reason rather than a silence

**Context:** three payment facts were unrecorded, and one is the commonest defect in Iranian gateway integrations. ADR-022's amendment had just made `IRR` the stored currency; **nothing said what unit crosses the wire to a provider**, while ADR-023 item 5 turns a wrong guess into a security event. `supportsDirectDebit` had been a flag with no flow behind it since ADR-023 was written. And ADR-023 is titled *"…and Iranian PSP Profile"* and profiles no PSP. Documentation-only: no migration, no table, no feature code.

**Options considered:**

- **Where to record the granularity consequence.** It was discovered as one thing and is two: a **provider property** (what increments a gateway can charge) and **tax arithmetic** (how the total comes to land on one). Split deliberately — granularity to ADR-023, rounding to ADR-055, cross-referenced. Putting both in one ADR because they were found together would couple ADR-055's arithmetic to ADR-023's port.
- **Whether to profile actual PSPs.** No. ADR-023's own *Adding a new provider* section requires a gateway to cost *"Zero changes to Application, Domain, or any other adapter"*, and a vendor list inside an ADR is that coupling, plus a list nobody re-checks. **The ADR owns the questions; the adapter owns the answers.**
- **Whether the wire-unit hazard needs a risk row.** No — reasoning below.

**Decision:**

**Part A — the wire unit is declared, never assumed.** `PaymentProviderCapabilities` gains a declared divisor between the stored minor unit and the unit the provider's protocol carries. **Named for the wire, not for display**, because ADR-022 item 4's presentation divisor is a different number with a different consumer and **both are 10 for `IRR`** — indistinguishable at a call site unless the names separate them. Conversion happens in exactly one place, the adapter; verify converts back so item 5's comparison is always Rial against Rial.

**The two failure modes are not symmetric, and that asymmetry is the whole reason for the amendment.** Sending Tomans against a Rial intent fails item 5 loudly on every *successful* payment. **Converting out but not back — or with the wrong factor — compares equal and passes.** The second is silent and takes real money tenfold. A suite that only asserts "verify succeeds" cannot see it, which is why the amendment adds a **unit round-trip assertion to ADR-023's existing shared adapter contract suite**: given N Rials, the outgoing payload carries what the declared divisor implies, *and* a response echoing that value verifies back to exactly N. Written once, run by every adapter.

**The Rial-versus-Toman claim is marked unverified against any vendor's primary documentation**, in the house style. It does not weaken the ruling: **a port that declares its unit is correct whether or not any given gateway is Toman-denominated**, and it is precisely because the answer varies by vendor that a declaration exists instead of a constant.

**Part A4 — a Toman gateway cannot charge every Rial amount, and the tax absorbs it.** Only multiples of 10 stored minor units are representable, ADR-055 makes the charged figure the gross amount, and a percentage of a round number is routinely not round. **Not fixed by rounding in the adapter** — that would alter an amount between invoice and charge and break item 5 by design. The ruling: the port declares a **charging granularity**, an off-granularity amount at the adapter is a **hard failure**, and ADR-055's own amendment carries the arithmetic.

**The arithmetic was computed, not asserted**, and the precise statement matters because the obvious shorter one is wrong. `tax_amount_minor` is the value **nearest the nominal tax such that `subtotal + tax` lands on the granularity** — not "the tax rounded to the granularity". With a subtotal of 59,999,999 at 10%, rounding the nominal 5,999,999.9 to the nearest 10 gives 6,000,000 and a total of 65,999,999, **which is not a multiple of 10 and cannot be charged.** Four cases were computed (60,000,000 and 59,999,990 and 59,999,999 at 10%, and 85,000,000 at 9%): in every one `subtotal + tax = total` exactly and the total lands on the granularity, with the tax deviating from nominal by at most **1.1 IRR — a fraction of one Toman.** That deviation is accepted deliberately, and the ADR says why: an invoice that reconciles and a charge the gateway can take are both required, and the nominal rate is a computation basis rather than a figure owed to the Rial.

**One consequence recorded so it is not met as a surprise in a test:** two invoices with the same subtotal and rate can carry **different** tax through providers of different granularity — which is why those columns are snapshotted per invoice rather than recomputed.

**Part B — ADR-058: direct debit is not used in V1, and the second reason is the blocking one.** No adapter declares `supportsDirectDebit` true; the flag stays in the port, and ADR-023 item 1's existing *"must fail at startup with a configuration error"* does the enforcing with nothing new written.

**ADR-037's deferral is stated more precisely in the ADR than the session brief stated it**, and the precision is what makes the argument work. ADR-037 **guarantees** the database never holds credential material — a `secret_ref` locator only, and *"No plaintext secret is ever written to this table, by any code path."* What it **defers** is the resolver: *"Until a resolver exists, a `secret_ref` resolves from configuration"* — an environment variable — with the mechanism owed *"before the first live provider credential is stored."* **So the accurate framing is not "a mandate under a deferred mechanism" but "a mandate in an environment variable"**, and the argument is about what the credential can *do*: a gateway key authorizes *asking* for a payment the customer is approving in a redirect; **a mandate authorizes pulling money from a bank account with nobody watching.** ADR-037's trade was scoped to the first class; adopting direct debit would silently widen it.

The other two reasons: the plans are annual and invoice-and-notify is the right shape for a once-a-year charge; and a mandate revoked or expired **between** periods is neither `PAST_DUE` nor a payment failure, so it would need a new arc in ADR-024 item 3's transition list — **adding that arc later is an ADR, adding it accidentally is a bug** that silently expires customers whose bank let a mandate lapse. Four reopening conditions are recorded as a set, including that the new transition must fall back to invoice-and-notify **rather than toward expiry**.

**The backfill test returns "may wait", and the reading is sharper than the brief's.** Both halves point the same way. `billing_payment_events` is append-only and a mandate identifier is **legitimately empty on every redirect payment** — ADR-056's test, applied consistently. And the table that would need a *discriminator*, `billing_payment_intents`, is **not on §5's append-only list**: it is mutable by design (ADR-045 gives it a `version` column because *"the verify callback and the reconciliation sweep both write status"*), so a `charge_source` column added later **can be backfilled** to `REDIRECT`. That is exactly the case `document_type` on `invoices` was not, and **the difference is the `REVOKE`.**

**Part C — the profile is a checklist.** Ten things must be established from a vendor's own then-current documentation before its adapter is written, each tied to a rule it serves. **One gap it exposes and does not close:** the checklist asks for a **minimum** transaction amount and `PaymentProviderCapabilities` declares `maxAmountMinor` with no counterpart. Noted rather than fixed — inventing a field before an adapter needs it is the speculative shape `AGENTS.md` §4 warns against, so **the first adapter whose provider has a minimum adds it.**

**No risk row was opened for the wire-unit hazard, and this is a judgement rather than an omission.** It has a declared port field, a **mandatory shared contract test** that catches the silent form specifically, and a checklist entry. **A hazard with an owned, specified control is a design decision, not an open risk**, and a row would restate the ADR without adding a trigger anyone would pull. **R-015 gained a dated addendum instead** — it already records that provider selection has no phase and that *"modeling a first adapter's fixtures still means choosing"* a provider, and Part C's checklist is precisely what that choice must answer. Its status is unchanged: nothing was chosen and no phase owns choosing.

**`PHASE_2_BRIEF.md` §5's Money rules gained the constraints; §4 gained no table, and the amendment says so explicitly** — because a reader who sees a mandate discussed in ADR-058 will look for one, and ADR-058 creates nothing. `05_API_CAPABILITY_CONTRACTS.md` needed nothing: `billing.payment.initiate`'s contract speaks `MoneyDto` in stored units, which is exactly what part A2 requires, and the wire unit never crosses that boundary by construction.

**Status:** **RESOLVED.** All three gaps are recorded ahead of item 12, which was the deadline for the first two. **Owed and tracked:** a minimum-amount field on the port when an adapter first needs one; every value in Part C's checklist, per vendor, when its adapter is written (**R-015**); and ADR-058's four reopening conditions, which are a set rather than alternatives.

## 2026-09-03 — ADR-056 and ADR-057: two shapes `invoices` cannot gain later

**Context:** ADR-048 fenced credit notes out of its own scope, and ADR-055 fenced the buyer's tax identity out of its. Both fences were correct — those ADRs were about numbering and about tax arithmetic. But the part of each that **cannot wait** is a column on an append-only table, and item 13's creating migration is the last moment either can be free. Documentation-only: no migration, no table, no feature code.

**One rule decides both, and it is recorded in the ADRs rather than only applied**, because it is what a later reader needs to judge the next column someone proposes: §5 revokes `UPDATE` and `DELETE` on `invoices`, so a column can still be **added** later — what can never happen is **filling it in for rows that already exist**. **A column must exist at creation if old rows would need a real value in it; it may wait if old rows are legitimately empty.** `document_type` and the buyer snapshot fail that test; `corrects_invoice_id` passes it and waits.

**Options considered:** the rulings were the maintainer's. Three judgements were this session's, and one of them overrode the session brief.

- **Whether the profile table takes a `version` column.** The brief said yes *"per ADR-045 … confirm that from ADR-045 rather than taking it from here."* Confirmed, and **it does not hold.** See below.
- **Whether to open a new risk row for the purge/PII tension.** No — R-043 already owns it. Reasoning below.
- **Whether a capability had to be added to §3.** Yes, and it was checked rather than assumed.

**Decision:**

**ADR-056 — correction documents.** `invoices` carries `document_type`, `NOT NULL`, `INVOICE` | `CREDIT_NOTE`; **Phase 2 issues only `INVOICE`** and nothing can write a credit note. **The ADR answers the ADR-046 objection explicitly, because a reviewer will raise it and would be right to:** ADR-046 refused to reserve `deleted_at` on ~20 tables because a nullable column set by nothing is a permanent obligation on every reader. `document_type` is the opposite on every axis — `NOT NULL`, set by every row to a true value, and a reader that ignores it still reads a correct invoice. **It is a discriminator, not a reservation**, and without that line the two rulings look contradictory when they are the same principle reaching opposite conclusions on different facts.

**One number series, not two.** ADR-048 part 1's reason decides it: *"the issuer of these invoices is one legal entity — the platform — and a seller keeps one invoice book."* A credit note is issued by that seller into that book, so it draws from the same counter and **`invoice_number_counter` does not change.** The rejected alternative is recorded with its trigger: a separate series per document type is the conventional accounting shape, and if a filing or a two-way integration ever demands one, ADR-048's *"Why this blocks any two-way accounting integration"* applies in full.

**Amounts are always positive; the document type carries the sign** — because ADR-022 item 5's allocator requires that the sum of parts equal the whole exactly, and negative amounts make every aggregate ambiguous about whether a sign has already been applied.

**Tax on a correction follows the invoice it corrects, not the rate of the day.** This is the non-obvious one: **a correction must reverse the arithmetic that actually happened.** A credit note issued after a VAT rate change, carrying the new rate, would reverse an amount that was never charged and leave a residue reconciling against nothing.

**Voiding is recorded as a consequence, not a choice.** The application role cannot `UPDATE` or `DELETE` an issued invoice — a database privilege, not a policy — so the correction path is a new document **necessarily**. The ADR says it that way so nobody looks for a void operation that cannot exist.

**ADR-057 — the buyer's legal identity.** A mutable tenant-owned `billing_profiles` table (legal type حقیقی/حقوقی, legal name, national identifier, economic code, registration number, address, phone) and an **immutable snapshot on the invoice, as explicit columns rather than a JSON blob** — because an append-only record wants a fixed inspectable shape, and JSON's advantage is that it can change without a migration, which is exactly the wrong property for a row nothing may update.

**Two independent reasons for the timing, and neither alone would justify it.** ADR-044's principle, already applied to this table twice (ADR-048 for the number, ADR-044 for the line description): **who the invoice was issued *to* is part of what the invoice *is***, and a foreign key to a mutable profile is not a substitute, because the profile changes when a company renames and the invoice must not. And **R-043**: an invoice without the buyer's identity is **permanently unregisterable** with سامانه مودیان, since the row cannot be updated.

**The `version` column was refused, and this is the session's correction to its own brief.** ADR-045's ruling is **a named list of four tables, not a rule about mutability.** Its Tier 2 position is explicit: six named mutable tables get **no** column, *"on ADR-046's logic applied to columns — a field is added in the same slice that adds its enforcement, never ahead of it"*, with the trigger *"the first slice that gives any one of them a second writer"*; and every Tier 1 justification names two concrete writers. **`billing_profiles` has exactly one Phase 2 writer** — items 12 and 13 read it. So by ADR-045's own terms it is Tier 2-shaped and takes no column. **Adding one because the table happens to be mutable would depart from a ruled ADR while appearing to comply with it**, which is worse than either following it or overruling it openly. The accepted cost — two administrators can lose one another's edit — is stated in the ADR with a checkable reopening trigger, on exactly the reasoning ADR-045 used for `billing_refunds` and the two override tables.

**No invoice without a profile**, so the buyer supplies it **before** ADR-023 item 2's redirect. **Two things now happen at that step** — ADR-055's tax breakdown must also be shown before it — and the ADR states them together so item 12's implementer meets them in one place. **A trial is exempt**, and the ADR is careful about how it says so: ADR-052 rules `plan.subscribe` starts a trial with *"no payment"*, and its verification asks for *"a subscription in `TRIALING` with no payment"* — **it does not say "no invoice" in those words**, so the exemption is recorded as an inference (an invoice is the record of a charge; a trial charges nothing) rather than quoted as text.

**A capability was owed and had to be added by the brief, not by the ADR.** Checked one by one: none of `05` §4.2's fifteen writes tenant profile data of any kind, and neither does Phase 1's list — `organization.create` takes a name and a slug. **ADR-057 states the obligation and declines to discharge it**, on ADR-048's precedent that *"amending this list is a scope decision belonging to this file — `AGENTS.md` §1 authority #2 — and not to an ADR."* `PHASE_2_BRIEF.md` §3's amendment adds **`billing.profile.set` (tenant / MEDIUM_WRITE, item 13)** as the other half of the same change, ratifying sixteen capabilities. §5's permission rule binds it to `owner` and `admin` only (D2-8), which is right for a capability that sets the organization's legal and tax identity.

**The purge tension got a proposal, marked as one.** ADR-020 rule 4 excludes financial records from purge **and in the same sentence** requires them *"reduced to the minimum fields required"* — which is not self-executing. ADR-057 proposes the split: legal name and entity identifiers kept, phone dropped, address reduced, and **a natural person's کد ملی dropped while a legal entity's شناسه ملی is kept** — public register data versus the most sensitive field on the row. **Explicitly marked unverified against the Iranian legal minimum**, in the house style, with the natural-person line named as the one most likely to be wrong. **No new risk row was opened for it:** R-043 has the same subject, the same owner (maintainer plus accountant) and the same resolution, and splitting it would fragment one decision across two rows. R-043's addendum records it.

**R-043 gained an addendum and did not move.** ADR-057 removes one blocker — invoices issued from now on carry what a filing needs, instead of being permanently unregisterable. **It closes nothing:** the registration decision is regulatory, no schema discharges it, and the seller's own identity and ADR-048 part 5's tax unique number both remain fenced to a سامانه مودیان slice that belongs to no phase.

**`04_DATABASE_BLUEPRINT.md` was checked again and deliberately left alone.** §2.5 lists `invoices` with no column list at all — so nothing there is contradicted by adding `document_type` or snapshot columns, and `04` describes itself as a conceptual baseline whose exact columns are finalized per slice. Nothing stale, nothing written.

**One thing in the session brief was wrong** — the `version` column, above. It is worth noting *how* it was caught: the brief itself said to confirm the claim against ADR-045 rather than take it on trust, and confirming it is what showed it false. **The brief's other assumptions held**: ADR-056, ADR-057 and R-044 were all free, and the append-only reasoning behind both rulings is exactly as it described.

**Status:** **RESOLVED.** Both rulings are recorded ahead of item 13's migration, which was the deadline; the capability the second one owed is discharged by the file that owns capability scope; and every gap either ruling leaves is named with a trigger rather than left implicit. **Owed and tracked:** R-043's registration decision and the legal verification of the purge split; the seller's own registration identity; national-identifier validation algorithms (the implementing slice's); refund documents as distinct from credit notes; and `corrects_invoice_id`, which arrives with the slice that issues the first credit note — the slice that gives `billing_refunds` a capability, and does not exist.

## 2026-09-03 — two money rulings recorded: tax on a subscription purchase, and Rial/Toman

**Context:** two maintainer rulings, both about money, both binding on the creating migrations of Phase 2 items 12 and 13, and neither recorded anywhere. Both touch `invoices`, which `PHASE_2_BRIEF.md` §5 puts on the `REVOKE UPDATE, DELETE` list — and **a column can be added to an append-only table later while the rows already in it can never be filled in.** That asymmetry, not migration order alone, is why these were recorded before item 13's migration rather than during its slice. Documentation-only: no migration, no table, no capability, no feature code.

**Options considered:**

- **A new ADR for each, or an amendment for one.** Tax got its own ADR (**ADR-055**, confirmed free from the file — the highest existing was ADR-054). The Rial/Toman ruling is a **dated amendment to ADR-022**, because money has one home and item 4 of that ADR already states the principle it makes specific. **The amendment convention already existed in that file** and was followed rather than established: ADR-006 (2026-08-28), ADR-010 (2026-08-28) and ADR-054 (2026-09-03) all carry `### Amendment, <date> — <what>` sections.
- **Whether to open one risk row or two.** One. Reasoning below.
- **Whether `04` and `05` needed dated notes.** Neither did. See below.

**Decision:**

**Ruling one — ADR-055, `ACCEPTED (new)`.** The published price is **net**; VAT is added at checkout; no `tax_inclusive` flag is added, because net is universal here and a flag would be a configuration point with exactly one value — the defect ADR-046's ruling describes. Two interface obligations are recorded so the ruling is not a licence to surprise a buyer: a price shown anywhere must state that tax will be added, and checkout must show subtotal/rate/tax/total **before** the redirect.

**The consequence that fails loudly and is invisible from either ADR alone: `billing_payment_intents.amount_minor` is the GROSS amount.** ADR-023 item 2 persists the intent before the redirect; item 5 compares the provider-reported amount against it and calls a mismatch *"a hard failure and a security event, never an auto-accept."* **Persist the net amount there and every verification fails as a security event, on every purchase**, escalating through item 4's `provider-unknown` path into a human queue. `04` §2.5 lists that column without saying which figure it holds; ADR-055 says which, and a cross-reference line was added to ADR-023 pointing at it without restating it.

**`invoices` gains four `NOT NULL` columns created with the table** — `subtotal_minor`, `tax_rate_bp` (basis points, an **integer** because ADR-022 item 2 forbids floating point on monetary columns and a rate carries the same hazard), `tax_amount_minor`, `total_minor` — with currency alongside per ADR-022 item 8. **A zero rate is `0`, never `NULL`:** on a table nothing may ever `UPDATE`, the ambiguity between "zero" and "not computed yet" is permanent rather than temporary. **Tax is a header figure, not a line**, because ADR-044's ruling requires every line to carry its own denormalized description and a tax line's description would be a computed artifact rather than a description of anything sold.

**"Configurable" was ruled to mean a dated table, not a settings value, and the reasons are concrete.** Iran's VAT rate has actually changed within the platform's planning horizon, so a single mutable value makes *"what rate applied on the day this invoice was issued"* unanswerable from the configuration — and carries no record of who changed it or when, which is the first question after a wrong rate reaches a customer. So: **`tax_rates`, platform-global, append-only, one row per rate period**, resolved as the greatest `effective_from` not in the future, corrected by appending a superseding row. **The redundancy with the invoice snapshot is deliberate and is named in the ADR because a reviewer will call it duplication:** the snapshot makes an issued invoice self-contained, the table makes the platform's rate history auditable, and dropping either loses something the other does not supply.

**Rounding was not re-ruled.** ADR-022 item 5 already says *"Proration (ADR-025) and tax must use the allocator, not independent rounding"*; ADR-055 cites it and adds only the consequence specific to this market — `IRR` has zero minor units, so tax is a rounding **of whole Rials**, and the mode must be declared where tax is computed.

**Ruling two — ADR-022 amendment, items 9 to 13. Most of it was already true, and the amendment says so rather than claiming credit.** This is the session's main finding and it changed how the amendment is written.

**Phase 1 already built this.** `20260822110000_money__create_currencies.sql` seeds `IRR` with `minor_units = 0`, `presentation_code = 'IRT'`, `presentation_divisor = 10`, `presentation_symbol = 'تومان'`, and its own comment already reads *"amounts are stored in rial and shown in toman, a factor of 10 that must never appear as a literal in code."* **And it is enforced structurally, not by convention** — verified rather than assumed: the `Currency` domain entity carries only `code`, `name` and `minorUnits`, and `CurrencyRepositoryPg` selects only `code, name, minor_units`, so **the presentation columns are never read by any code path that exists today.** Items 9, 10 and 12 are therefore a confirmation being made normative, not a change of behaviour, and the amendment labels them that way.

**Items 11 and 13 are genuinely new.** Item 11: **machine-readable output carries the stored currency, never the display unit** — `schema.org` `Offer.price`/`priceCurrency`, Open Graph tags, feeds and every API response emit `IRR` and the Rial amount. The reasoning is what makes it non-negotiable: **"Toman" is not an ISO 4217 code**, `IRT` is this platform's own label, and a consumer receiving it either rejects it or **reads it as Rials and is wrong by a factor of ten, silently**, in a price a search engine shows a shopper. Item 13: **the rendered invoice is denominated in Rials** while the UI shows Toman — recorded as an exception *with its reason*, because the inconsistency is visible and someone will eventually "fix" it in the wrong direction. The correct direction is the invoice, whose figures must match the ledger.

**One risk row opened, one judged unnecessary, and both judgements are recorded rather than assumed.**

**Opened — R-043:** the platform will issue invoices as a legal entity and register none with سامانه مودیان, and no phase owns doing so. ADR-048 part 5 deferred the tax unique number with the named trigger *"the slice that integrates with سامانه مودیان"* — **and that slice belongs to no phase, so the deferral has a trigger nothing will ever pull.** Verified that no existing row covers it: the register contains no row mentioning tax, VAT, currency or مودیان. The row is honest about its axis — **it cannot be closed by writing code**, its owner is the maintainer plus an accountant, and its useful marker is a deadline (before the first invoice to a paying customer) rather than a reopening trigger. It also records the one part that *is* a schema question and carries the same append-only trap: the buyer's tax identity, which nothing collects and which an issued invoice can never gain later.

**Not opened — a display-unit value reaching machine-readable output.** Tempting, and it is a real ten-times-wrong failure, but it is **structurally impossible today** by the verification above: the divisor is never applied anywhere in code, the entity cannot see it, and the repository does not select it. ADR-022's new item 11 now owns the rule and carries its own verification bullet. Opening a row for a rule a new ADR item already owns, against a failure current code cannot produce, would be padding the register rather than tracking a risk.

**Two files were checked for staleness and deliberately left alone.** `04_DATABASE_BLUEPRINT.md` §2.5 lists `billing_payment_intents.amount_minor` **without saying whether it is net or gross** — that is underspecified, not stale, and `04` describes itself as a conceptual baseline whose exact columns are finalized per slice. ADR-055 outranks it in `AGENTS.md` §1's order and now states which. `05_API_CAPABILITY_CONTRACTS.md` needed nothing: its `MoneyDto` definition and every worked example already use `IRR` with `minorUnits: 0`, which is exactly what ruling two makes normative.

**One thing in the session brief was wrong, and in the direction that mattered.** It expected Step 1's answer to be *"only the `Money` contract type, if that"*. In fact a whole `modules/money` exists — value object, `Currency` entity, repository, contracts, a `currencies` table with five seeded currencies spanning minor-unit exponents 0, 2 and 3, and the `IRR`/Toman presentation pair already configured. Had the amendment been written to the brief's expectation it would have presented settled Phase 1 facts as fresh rulings, which is a small dishonesty that compounds. **Step 1's actual gate — is a Toman value stored or emitted anywhere — passed cleanly: none is**, so ruling two is a first record and not a correction.

**Status:** **RESOLVED.** Both rulings are recorded ahead of items 12 and 13, which was the deadline; `tax_rates` is added to §4 by the file that owns that list (29 → 30) with its RLS exemption and its place on the append-only list; and the gaps neither ruling covers are named rather than left implicit. **Owed and tracked:** R-043's registration decision and the buyer tax identity it names; **tax on a mid-term plan change**, owed to item 15 and flagged in ADR-055 as the edge most likely to be hit first, since a prorated amount and a tax computation on the same figure are two roundings and ADR-022 item 5 requires the allocator for both; and tax on a refund or credit note, which waits on a credit-note decision that does not yet exist.

## 2026-09-03 — ADR-041 ruled with a fifth option, and the tripwire that makes it enforceable

**Context:** the session two entries below answered ADR-041's four PostgreSQL questions empirically and **withheld** the ruling, because the answers disqualified the option that was about to be adopted. The maintainer read those transcripts and ruled. The ruling is **none of ADR-041's four options**, and the enforcement it depends on is the only code this session wrote.

**Options considered:** the ruling was the maintainer's. Two judgement calls were this session's, and both were settled from the code rather than from preference.

- **Where the tripwire lives.** `tools/conformance/lib/exceptions.ts` matches an exception on `rule` + `file` alone — `exceptions.find((e) => e.rule === violation.rule && e.file === violation.file)` — and a grep across `tools/` finds **no per-rule opt-out of any kind**. So the harness *cannot* mark a rule non-exceptable, and as a conformance rule this one could be silenced by a single `exceptions.json` entry — an entry that would silence a **real cross-tenant hole** rather than a cosmetic violation. It went outside the harness as `npm run check:partitions`, following the `check:register` / `check:dist-deps` precedent, for exactly the reason those were placed there.
- **Whether `04_DATABASE_BLUEPRINT.md` §8 needed a note.** It did not, and nothing was written. §8's index list would change in *meaning* only if something were partitioned — indexes on a partitioned table are declared on the parent and propagate — and the ruling partitions nothing. Writing a note would have implied a change that did not happen.

**Decision:**

**ADR-041 → `ACCEPTED (was OPEN)`. Option 5: keep the append-only tables partition-*compatible*, and do not partition them.** No partitions, no `audit_events` conversion, no partition machinery. **Inventing a fifth option inside a ruling is unusual enough that the ADR justifies it rather than slipping it in:** the four options were drafted before anyone had run a statement against a partitioned table, and the empirical section did not merely add caveats to option 1 — it moved the price.

**Three findings raised option 1's cost**, each with a transcript already in the ADR: partitioning **weakens tenant isolation** under this project's configuration (R-042), and the remedy is a precondition that must hold for every partition forever; it **permanently surrenders database-enforced uniqueness on `id`**, irreversibly; and **the partition-creation job is not buildable as imagined** — `nexora_app` is `NOSUPERUSER` and owns nothing, so partitions can only be created by migrations, committing the platform to a recurring migration obligation nobody had costed. **And the benefit does not arrive yet:** detaching a partition needs somewhere to put it, and R-025 records that no object storage port exists. Until Phase 2.5 buys that, partitioning bounds scan size and frees no disk at all.

**The limit of option 5 is stated in the ADR rather than glossed.** A table cannot be `ALTER`ed into a partitioned table — conversion always means a new table, a full row copy and a swap — so **option 5 makes the future copy no cheaper, not by one row.** What it preserves is narrower and worth more: that the conversion will not *also* have to break a contract other code depends on, which is the expensive part of a late conversion.

**The four-table list was narrowed, and the reason is on the record.** `invoice_lines` is dropped from ADR-041's own list of candidates: it was grouped with the ledgers by **shape** (append-only), and **ADR-048's volume statement — written after ADR-041 — is the fact that separates them by growth** (*"thousands of invoices per year, not thousands per minute"*). The ruling states a **rule** rather than a list, so a later table can be classified without reopening the ADR: a candidate's row count grows with platform *activity*; a non-candidate's is bounded by *business volume*. `outbox_events` and `outbox_event_deliveries` are neither partitioned **nor bounded**, and that is recorded as owed to Phase 2 item 14 rather than left implicit.

**Part 3 rule 3's collision with ADR-023 item 4 is real but conditional, and the ADR says which.** Item 4 requires that *"an intent may never be verified twice into two ledger entries"*, and Phase 2 item 12 owns it. A unique index on `billing_payment_events` excluding the event column would permanently exclude that table from partitioning — **but ADR-023 item 4 does not ask for one.** Its own first sub-bullet says *"the sweep is idempotent through ADR-009"*, and ADR-009's uniqueness lives on `idempotency_records`, not on the events table; a status transition on `billing_payment_intents` would also satisfy it. **So the likely outcome is no collision at all**, and the obligation on item 12 is to record the exclusion *if* it chooses the index — not to avoid the index. The session brief framed this as a live collision; reading item 4 and item 12's scope shows it is a fork, and the ADR is written on the fork.

**Retention windows are recorded, and their epistemic status with them.** Financial and tax records 10 years, `audit_events` 2 years then archived, deletion-recording audit events never removed. **The ten-year figure is the commonly cited reading of ماده ۱۳ قانون تجارت and was NOT verified against the primary published text**, and is marked that way in the ADR — the house style ADR-041 and ADR-048 both established. Nothing in Parts 1–5 depends on it. **The ADR states plainly that no job implements any of this and none can until R-025 closes**, so that a reader cannot mistake a recorded window for an enforced one.

**The tripwire, which is the whole reason this is more than a paragraph.** `npm run check:partitions` fails the build if any relation with `relispartition = true` lacks its own `relrowsecurity`/`relforcerowsecurity`, lacks a `pg_policies` row of its own, or is directly reachable by the application role — Shape B plus Shape A, enforced together. **It matches nothing today and is therefore free**; it fires on the first partitioning migration, before the merge rather than after the incident. The app role name is read from the connection string rather than hard-coded, so renaming the role cannot silently un-check it.

**It was proven to fail before it was trusted** — ADR-030's standard, and the checkbox the previous session left half-met. A fixture builds the exact vulnerable shape (the `audit_events` three lines on a partitioned parent only, with `001_roles.sql`'s grant mechanism reproduced in the throwaway schema so the fixture models production rather than an invented weakness), observes the check **red with all three violations and exit code 1**, applies the remedy, and observes it **green with exit code 0**. **Shape B alone left `PARTITION-APP-PRIVILEGE` still firing** — the fixture's own demonstration of why the ruling adopts A *alongside* B rather than instead of it. The fixture asserts its own schema is gone afterwards, because a leftover partitioned table would turn every later run permanently red.

**Two facts were re-established rather than inherited.** Nothing foreign-keys `audit_events` — checked statically across every `.sql` and live against `pg_constraint`, zero rows — so Part 3 rule 2's premise holds. And the grant finding still describes the live database: a table created **in `public`** today with no explicit `GRANT` shows `DELETE, INSERT, SELECT, UPDATE` for `nexora_app`, with `pg_default_acl` carrying one entry, `{nexora_app=arwd/nexora_migrate}`. **A precision worth recording, because it nearly produced a false refutation:** the same test run in a *different* schema shows **nothing**, since `001_roles.sql` scopes the default privilege `IN SCHEMA public`. The finding is real; a careless re-test of it is not.

**`R-030` moved `OPEN` → `ACCEPTED`**, which is the register's word for a risk retained by an evaluated decision. Deliberately not `RESOLVED`: growth is now **owned and bounded by a stated trigger**, and is **not reduced** — nothing is archived, nothing deleted, and every table still grows exactly as fast as yesterday. **`R-042` stays `OPEN` and is now guarded**: no partition exists so nothing is exposed, its trigger is still the first partitioning migration, and the check enforces the answer. One thing remains owed verification and is named rather than assumed — whether a policy on a partition and a policy on the parent are **both** applied when a row is reached through the parent. Neither session tested it.

**Two things in the session brief were wrong and are recorded rather than worked around.** Its Part 5 says the default privileges grant on *every* partition without qualification — they are scoped `IN SCHEMA public`, which matters to anyone re-testing. And it framed the ADR-023 item 4 collision as certain; it is conditional on item 12's implementation choice, and item 4 itself points at the mechanism that avoids it.

**Status:** **RESOLVED.** ADR-041 is ruled ahead of Phase 2 item 4, which was the deadline; its defective verification item is replaced with the old wording kept visible and an explanation of what it got wrong; and the ruling's precondition is enforced by a check that has been observed to fail. **Owed and tracked elsewhere:** the parent-plus-partition policy interaction (ADR-041 Part 5), `outbox_events`' removal policy (Phase 2 item 14), the ten-year figure's primary-source verification, object storage (R-025), and item 12's recording obligation if it takes the unique-index fork.

## 2026-09-03 — ADR-041's four questions answered empirically, and the ruling deliberately withheld

**Context:** ADR-041 (`Ledger and Audit Table Growth`) has been `OPEN` since 2026-09-01 with a verification list whose first item forbids a ruling until four PostgreSQL semantics questions are answered *empirically* — they were recorded as *"owed verification"* rather than asserted, because the pass that wrote the ADR was documentation-only. Phase 2 item 4 creates `subscription_periods`, the first append-only table the decision binds, and ADR-041's own timing argument is that partitioning an empty table is a schema change while partitioning a populated one is a data migration under forward-only migrations (ADR-021 item 8). The session was to answer the four questions and then record a ruling adopting option 1 (native declarative partitioning by month).

**The four questions were answered. The ruling was not written.** That is the outcome, and it is the correct one.

**Options considered:** the session brief was explicit that if the probe contradicted its premises the ruling must not be recorded — *"Part 1 in particular assumes partitioning does not weaken tenant isolation; if Step 1 shows otherwise, the ruling is wrong and must not be written."* It does show otherwise. The choice was between recording the ruling with a caveat attached and withholding it; withholding is right, because the defect is not a caveat on the ruling but a precondition the ruling has no text for, and a ruling that is 90% correct about tenant isolation is worse than an open question.

**Two premises in the session brief did not survive contact and are recorded rather than worked around:**

- **"Docker available"** — it is not installed on this machine, which `CLAUDE.md` already states. The probe ran against the native PostgreSQL **17.5** the test suite uses, with the project's real `nexora_migrate`/`nexora_app` role split. CI runs `postgres:17-alpine` (17.11); both are PostgreSQL 17 and nothing found is version-sensitive within a major release, but the transcripts say 17.5 rather than claiming to be CI's build.
- **"partitioning does not weaken tenant isolation"** — false under this project's configuration. See below.

**Decision:**

**Q1 and Q2 — the finding.** With the *identical* three lines the `audit_events` migration uses (`ENABLE ROW LEVEL SECURITY`, `FORCE ROW LEVEL SECURITY`, one `USING` policy on `current_setting('app.tenant_id', true)`) declared on a partitioned **parent**, and running as `nexora_app` with a **deliberately wrong** tenant context: access through the parent behaves correctly (0 rows; writes refused), and access addressed **directly at a partition** is not policed at all. `SELECT` returned **2 rows** where the parent returned 0 — the same 2 with **no tenant context set at all** — and `INSERT`, `UPDATE` and `DELETE` all succeeded against another tenant's rows. The probe's own final-state check, written before the result was known, records the damage: tenant 2 began with two rows and ended with one. **The unprivileged application role read, wrote, altered and destroyed another tenant's data, silently.**

**Q3 explains it:** `relrowsecurity`/`relforcerowsecurity` are per-relation and **not inherited** — the parent reads `t`/`t`, each partition reads `f`/`f`, and `pg_policies` holds exactly one row, on the parent. Partitions are ordinary tables with RLS switched off.

**Q4:** `information_schema.tables` reports the parent and every partition identically as `BASE TABLE`. So `tools/conformance/rules/schema-live.ts` would enumerate **all** of them, decided at **line 41** (`table_type = 'BASE TABLE'`), and each partition would fail its RLS check at line 87. **That puts the project in ADR-041's first branch — the harness flags every partition, loudly — not the silent one it feared.** Worth recording *why* the fear was misplaced: `schema-live.ts` reads `relrowsecurity` per relation from `pg_class` rather than trusting inheritance, so it cannot pass a partition it never checked.

**But ADR-041's branch analysis was aimed at the wrong problem, and this is the part worth carrying forward.** Both branches it names concern whether the *harness* is accurate. It would be accurate **and right**: those partitions genuinely have no RLS, and the violations are not false alarms. The real danger is the obvious response to the noise — an `exceptions.json` entry, which `CLAUDE.md`'s standing rule forbids and which here would suppress a live cross-tenant hole rather than a cosmetic complaint.

**Why this project specifically, verified rather than assumed.** `platform/db/init/001_roles.sql` grants through `ALTER DEFAULT PRIVILEGES … GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO nexora_app`, whose own comment says it applies to *"every table/sequence `nexora_migrate` creates from now on … no per-migration `GRANT` needed."* **A partition is such a table.** Reproducing that grant shape and creating a partition with no explicit `GRANT` anywhere: `nexora_app` holds `DELETE, INSERT, SELECT, UPDATE` on it automatically. The bypass is not an artifact of the fixture — the fixture reproduced production.

**A mitigation is proven, and option 1 survives with a precondition it did not have.** After `REVOKE ALL ON <partition> FROM nexora_app`, the direct `SELECT`, `INSERT` and `DELETE` fail with `permission denied for table`, while reads and writes **through the parent are completely unaffected**. Two shapes achieve it, and the choice is the maintainer's: **revoke on every partition** in both the creating migration and the ahead-creation job — narrow, but obeyed monthly forever, and one missed revoke is a silent month-wide hole; or **stop `ALTER DEFAULT PRIVILEGES` granting on new tables** and grant explicitly per table — structurally safer because an un-granted partition fails loudly, but it changes `001_roles.sql` for every table in the platform and every existing migration would need explicit grants. **Recommendation, advisory: the second, for its failure direction, with the first as an immediate guard if partitioning lands first.**

**Q0 — an obstacle neither the ADR nor the brief anticipated, hit before question 1.** `audit_events` declares `id uuid PRIMARY KEY`, and PostgreSQL refuses a primary key on a partitioned table that does not include every partitioning column. The repair is a composite `PRIMARY KEY (id, occurred_at)` — but **uniqueness on `id` alone cannot be recovered afterwards**, because a separate `UNIQUE INDEX (id)` is refused for the same reason. **Partitioning any of these tables permanently surrenders a database-enforced guarantee that `id` is unique.** Nothing breaks in practice (`gen_random_uuid()`, and every lookup is tenant-scoped), but it applies to all four candidate tables and belongs in the ruling rather than being discovered by whoever writes the first migration.

**A defect in ADR-041's own verification list, found by the list failing to catch this.** Item 3 asks for a cross-tenant proof *"against a partitioned tenant-owned table"* — a phrasing the **parent alone satisfies**, and testing the parent alone is exactly what would have missed all of the above. It needs a companion item naming **the partition** as the target. Recorded on the checkbox itself.

**What was recorded, and what deliberately was not.** ADR-041 gains the transcripts verbatim and **stays `OPEN`**; its §1.1 `Blocks` cell now says the questions were answered and the ruling withheld. Of its five verification checkboxes, **one was ticked** (the four questions, answered); the `schema-live.ts` item stays unticked because **no failing fixture was written**, which is ADR-030's actual standard and half the item; the cross-tenant item stays unticked because it was *proven and failed*. **Not written, all contingent on the ruling:** no `PHASE_2_BRIEF.md` §5 amendment, no `04_DATABASE_BLUEPRINT.md` §8 note, no retention windows, no partitioning job, no R-030 status change, and no `R-043` — the silent-pass branch it was reserved for did not occur.

**R-030's status is deliberately unchanged.** Its own finding — that these tables only ever grow and no document owns that growth — is untouched by the probe: no bound was set, no retention window decided, no partitioning adopted. Moving a *risk*'s status to record progress on its *investigation* would misreport it.

**Status:** **OPEN** — ADR-041 is still unruled, and now has a named precondition that must be settled first. **Nothing is partitioned today, so nothing is exposed today:** this is a defect found in a proposed design before it was built, which is precisely what ADR-041's verification list was for. Two things are owed before the first partitioning migration merges, both on **R-042**: the `001_roles.sql`-versus-per-partition-revoke decision, and a cross-tenant test that addresses a partition directly. The ten-year retention figure the brief supplied was **not** recorded, because it belongs to the ruling that was withheld — it is not lost, it is simply not yet a commitment.

## 2026-09-03 — ADR-051 implemented: the first production code of this programme

**Context:** ADR-051 was ruled `ACCEPTED` (Option B) earlier the same day and, like every ADR before it, implemented nothing. R-036 stayed `OPEN` on the explicit ground that *"a contract the running code does not yet obey is a divergence that still exists"*, and R-008 recorded occurrences 5 and 6 within about twenty minutes on documentation-only pushes — a green CI run had stopped being the default outcome of a merge, and every Phase 2 slice from here verifies against that build. The contract was already decided, so what remained was implementation rather than judgement. `/new-slice` was deliberately **not** invoked: that skill builds a new vertical capability, and this is a targeted change to two existing Phase 1 guards.

**Options considered:**

- **Step 1 was a genuine gate, not a formality.** A previous session recorded that Option B needs *"a session existed and was revoked"* to be distinguishable from *"no such session"* at guard time, called it ADR-029's territory, and explicitly refused to assume it. If revocation had been a `DELETE`, the ruled contract would not have been implementable without a schema change — a new decision, and not this session's to take. **It is an `UPDATE`.** `session-revocation.repository.pg.ts` sets `{ status: "REVOKED", revoked_at }` where `status = 'ACTIVE'`, and the migration declares `status text NOT NULL DEFAULT 'ACTIVE' CHECK (status IN ('ACTIVE', 'REVOKED'))` with a nullable `revoked_at`. The row survives and is fully readable. No schema change, no new decision.
- **How to expose "is this session revoked?" to `modules/tenant`.** A direct read of `sessions` from the tenant guard would have been shortest and is forbidden (`04` §1, `AGENTS.md` §4). Exposed as `CheckSessionRevokedService` through `modules/identity/contracts`, beside the two session ports already there. It answers one question with a boolean and cannot admit anyone, so it does not become a second authentication path.
- **Whether to change `ValidateSessionService`'s return type or bolt a second lookup onto the guard's failure path.** Changed the return type to a discriminated `SessionValidation`. One read instead of two, and — more importantly — the security reasoning then lives in one place next to the property it qualifies.

**A security property that had to be preserved rather than noticed afterwards.** `ValidateSessionService`'s existing doc comment states that it *deliberately* does not distinguish "no such session" from "expired" from "user suspended", because *"leaking which one occurred would help an attacker enumerate valid tokens."* ADR-051 appears to reverse that. It does not, and the code says why: **the split is exactly one case wide.** "No such session", "expired", "no such user" and "user suspended" all still collapse into one indistinguishable `INVALID`. Only an explicitly `REVOKED` row is separated, and **reaching that requires presenting a token whose hash already matched a real row** — so the only party who can observe the difference already held a genuine token, learns nothing they did not have, and is precisely the party ADR-051 exists to inform. Three unit tests pin the split at one case wide, including one asserting that an expired never-revoked session stays `INVALID`, so a later change that also started distinguishing expiry would fail rather than pass quietly.

**Decision:**

**`Session.isRevoked()`** is deliberately narrower than `!isValid()` and **takes no clock**: revocation is a stored fact, not a function of time, so a session that was revoked and has since also expired is still reported as revoked — telling its holder *that* is more useful than telling them it expired.

**`SessionGuard`** splits its single failure code in two. **`OrganizationAccessGuard` is where R-008's actual window closes:** `membership.revoke` commits the membership status change and the target's session revocations in **one transaction**, so a request can pass `SessionGuard` with a valid session and microseconds later find its own membership revoked — and the honest answer there is not "you are not a member" but "your session was revoked". The re-check runs **on the refusal path only**, after the guard has already decided to refuse, so the happy path costs nothing; and **only `FORBIDDEN` is reinterpreted**, every other error propagating untouched, because this is a refinement of one refusal rather than a general error handler. A live session still yields `FORBIDDEN`, which is ADR-051's scope limit exactly.

**Nine capabilities had to declare `SESSION_INVALIDATED`** — every one whose controller uses `SessionGuard`, which is all ten except `auth.login`, since login creates a session rather than consuming one. `ERROR-CODE-UNDECLARED` enforced this the moment the code was first thrown; the fix was to declare it, never to except the rule. `openapi.json` regenerated per ADR-033 items 4–6, and `ERROR-CODE-UNDOCUMENTED` needed nothing because `05` §7 already listed the code — verified rather than assumed.

**Four existing assertions changed, and none is a widening.** `auth.logout`'s "same cookie stops authenticating", both second-logout tests, and `membership.role.assign`'s session-invalidation test each assert a **specific** code on a genuinely revoked session, and that code is now `SESSION_INVALIDATED`. Every one became *more* specific. **Exit criterion 4 is unchanged and still proven** — the cookie stops working on the very next request; the code now says why.

**Nine new tests, at the two layers `AGENTS.md` §8 requires.** Five interface-contract tests, of which the two that matter most are the **scope limit** — `FORBIDDEN`, not `SESSION_INVALIDATED`, for a live session with no membership — without which nothing stops a later change turning every 403 into a 401 and calling it progress. Four unit tests on `CheckSessionRevokedService`, including that an expired-but-never-revoked session reports **not** revoked, and that a missing row reports not revoked so a vanished row cannot masquerade as a revoked one.

**What is not deterministically constructible is stated in the spec rather than implied.** The `OrganizationAccessGuard` branch is by definition a window *between two guards of one request*; opening it on demand requires instrumenting the guard chain, which would test the instrumentation. It is covered at two layers instead — a contract test proving the re-check runs and correctly preserves 403, and a unit test proving the revoked branch returns true. **`membership-revoke.integration.spec.ts`'s `losses` filter was deliberately not touched**: it already accepts 401, so whether the fix worked stays observable rather than hidden. No retry, no `retry: n`, no skip, no widened status set anywhere.

**The three status words, which are the part a future gate review will most need:**

- **R-036 → `RESOLVED`.** Its risk is *an undefined contract*, and a contract is eliminated by being defined and obeyed — both now verifiable by reading code and running tests, with no observation window needed.

The row names an observation window instead of declaring victory: **twenty consecutive green CI runs on `main`, or two weeks without an occurrence, whichever comes first** — a number chosen against the row's own ~15% estimated rate (itself flagged as under-estimating), so twenty clean runs would be surprising under the old behaviour and mundane under the new. It also names what would *falsify* the fix rather than merely delay confidence: a further occurrence whose dump shows a status other than `[200, 401]`.

**The amendment states what it does not touch and why, because all three concern one table and a later reader will otherwise assume two are redundant.** **ADR-053** is purging rows on a clock, for growth. **ADR-051** is the code returned to a request already in flight. **This** is which sessions a one-off operator recovery revokes. Three different things about `sessions`. Still undecided, and named: whether restored users are notified they were signed out, which is Phase 2.5's design work — ADR-024 item 10's notification obligation does not reach an operator-initiated recovery.

## 2026-09-03 — ADR-054: per-tenant recovery, and the two things it deliberately leaves unowned

**Context:** `RISK_REGISTER.md` **R-038** has recorded since 2026-09-02 that the only recovery mechanism this platform has is PostgreSQL physical point-in-time recovery, which operates on the whole cluster — so recovering one tenant rolls every other tenant back with it. For a platform whose entire isolation model is per-tenant, recovery was the one place tenancy did not exist. Earlier the same day Phase 2.5 was given the **export** half (ADR-020 rule 6). The **restore** half — the maintainer's actual requirement, *"store #357 broke, put it back"* — had no decision and no phase. Documentation-only session: no migration, table, module, capability, job or infrastructure.

**Options considered:** the granularity ruling was the maintainer's and is an input, not a conclusion drawn here. Four judgement calls were this session's:

- **Whether to state an RTO.** No. ADR-010's numeric targets are already flagged by dated amendment as unverified assumptions until `06` Phase 4 item 9, and a recovery-time number nobody has measured is worse than none, because it is the kind of number that gets quoted to a customer. What is stated is the *shape* — restore time scales with one tenant's volume rather than the cluster's — with the number owed to the first drill.
- **Whether to open a risk row for total cluster loss.** No — ADR-054 recommends one and does not open it, because the scope of a new row is the maintainer's to set. Recorded as a recommendation rather than silently skipped.
- **Whether to re-rate R-025.** No, but its staleness is recorded. See below.
- **Whether to restate or rename Phase 2.5.** Restated its framing; did not rename or split it. See below.

**Decision:**

**ADR-054 — Per-Tenant Recovery from Nightly Snapshots, `ACCEPTED (new)`, ruled by the maintainer on 2026-09-03.**

**The granularity ruling and what it bought.** Recovery granularity is **the last nightly snapshot: an RPO of 24 hours**, with arbitrary per-tenant point-in-time recovery **explicitly declined on cost**. The ADR records *why that makes it cheap*, because that reasoning is the thing a later reader would otherwise have to re-derive before pricing a reopening: arbitrary per-tenant PITR would have required all three of **continuous WAL archiving** (retained, monitored, and itself able to stop working silently), **a standby restore target** kept warm enough to replay into, and **a full-cluster restore per incident** from which one tenant's rows are then extracted — meaning recovery time scales with the whole cluster even when one tenant is affected. A nightly per-tenant logical snapshot requires **none of the three**. That is the difference between a scheduled job and an operational discipline.

**Snapshot and export are one mechanism, and the ADR says so rather than leaving it implied.** A nightly snapshot and a tenant's own data export are the same extraction on different schedules with different consumers — one unattended and written where an operator can reach it, the other on a tenant's request under their own quota. It is stated explicitly because two mechanisms for one thing is what `AGENTS.md` §4 forbids and what the idempotency rule already had to prevent once, and because **the specific failure mode is silent**: two independently-written extractors drift, one quietly stops covering a table the other covers, and nobody finds out until a restore is attempted. They are therefore built together and remain **separate deliverables** — the export is a capability with a quota, the snapshot is a job, the restore is an operator action.

**The ledger asymmetry, as a design property rather than a limitation.** Mutable tenant-owned rows are restored from the snapshot; the eight ledger-shaped tables are **never rewound** — verified against `PHASE_2_BRIEF.md` §5's seven (`subscription_periods`, `subscription_state_transitions`, `usage_ledger_entries`, `billing_payment_events`, `invoices`, `invoice_lines`, `outbox_events`) plus `audit_events` from Phase 1's own `20260822100100_audit__enforce_append_only.sql`, rather than recited from the session brief. **An invoice issued after the snapshot point stays issued**; undoing it is a compensating entry, which is what a financial record demands regardless of this ADR. Rewinding a ledger would be the defect, not the feature. The consequence is structural: the application role *cannot* delete a ledger row by design, so **restore is not something the running system can perform on itself** — it runs outside the application under a different role, as an **operator action with its own audit trail (ADR-034), never a tenant-facing capability.**

**A snapshot that has never been restored is not a backup.** A periodic automated drill restores a tenant into a sandbox and **verifies the result**, not merely that the restore exited zero. It carries its own verification checkbox rather than a sentence of prose, because it is the item every backup design drops first and discovers missing at the worst moment.

**Retention is 30 days, and the alignment is the reason.** It tracks ADR-020 rule 3's reversible-deletion waiting period so the platform has one retention number rather than two that drift apart. **One precision the ADR keeps:** rule 3 says the waiting period *default* is 30 days — a default, not a constant — so if it moves, snapshot retention follows it. The verification list has its own checkbox for that.

**The two things this ADR deliberately leaves unowned, both stated so a reader cannot close it believing more was solved than was:**

- **Total cluster or server loss.** A different risk with a different mechanism — physical backup plus off-site replication — and per-tenant logical snapshots do **not** substitute for it, because snapshots stored on infrastructure that is itself lost are not a recovery path. It is covered nowhere in this repository. **ADR-054 recommends a risk row and does not open one.**
- **Object storage, and this one blocks Phase 2.5's ability to build any of the recovery work at all.** Snapshots must be written somewhere and this platform has no object storage. `PHASE_2_BRIEF.md` §4 records `files` as out of Phase 2 with *"object storage, no phase owns it yet"*, and **R-025** already tracks it, confirming directly that no port exists (`platform/` holds only `clock.ts`, `config.ts`, `db/`, `http/`, `rate-limit/`) and no phase list delivers one. It is recorded as a **named prerequisite of Phase 2.5** rather than as an assumption inside the mechanism.

**A consequence this session caused and did not leave unsaid: R-025's own ratings are now stale.** It reads *"Low near-term — two full phases away from current work"* and *"Low today, Medium by Phase 3"* — both accurate when written on 2026-08-28, neither accurate now that ADR-054 makes object storage a prerequisite of the **next** phase blocking three of its four recovery items. R-025 carries a dated addendum recording that, with the superseded text preserved. **Re-rating its Likelihood and Impact cells is left to the maintainer** rather than taken as a side effect: this session's remit was ADR-054 and R-038, and a re-rating on an inherited external-review row should be deliberate.

**One further edge ADR-054 names rather than assumes:** what a restore does to a restored tenant's **sessions**. ADR-053 gives sessions a 30-day retention and `sessions` has no `tenant_id` at all, so it is not tenant-partitionable the way the snapshot mechanism assumes. Whether a restored tenant's users are logged out is unanswered, and an implementer should read that sentence as confirmation no answer was given.

**R-038's status word: `OPEN`.** Quoted from the row: *"nothing was built: no snapshot exists, no job runs, and a tenant that breaks tonight still cannot be recovered without rolling back every other tenant — the register reserves `RESOLVED` for a risk that is eliminated, not one that has acquired a good design."* The row also records that **ADR-020 rule 7's tenant-facing documentation obligation is now materially closer to an owner**: it needed a retention window to document, and ADR-054 supplies two concrete numbers — a 24-hour RPO and 30-day snapshot retention — so what was an obligation with nothing to state is now an obligation with content, still owed to whichever tenant-facing document Phase 2.5 produces.

**Phase 2.5 amended** in `PHASE_2_BRIEF.md` §9.6–§9.8 and `06_IMPLEMENTATION_PLAN.md`, dated, in each file's own style — the precedent for dated amendments in both was established earlier the same day. Items 4–7 added: snapshot job, operator restore, drill, and object storage as the prerequisite of the first three. The amendment says items 4–6 **share a mechanism** with the export capability already in §9.3, which is a different statement from being the same item, and records that they have **no dependency on the discount and referral work in either direction** — their only hard dependency is object storage.

**On Phase 2.5's framing, reported rather than done silently.** The phase was created as *Commercial Growth* and now carries operational resilience too. §9.8 records the unifying reading — **Phase 2 makes the product sellable; Phase 2.5 makes it responsible to run for real customers**: you can price it flexibly and you can be trusted with the data. **The caveat is recorded with it**: that reading is coherent but not forced, since nothing prevents selling at list price, so "must exist before the first paying tenant" is truer of the recovery half than the discount half. **The name `Commercial Growth` now under-describes the phase, and whether to rename it or split it is explicitly left to the maintainer** — a phase split is a maintainer decision and this session did not take it.

**Where the integrity check belongs — the question this session was told not to decide silently.** **ADR-030 does not admit it, and no amendment was needed, because a better home already exists.** ADR-030 is titled *Architecture Conformance Enforcement*; every check its §2 enumerates concerns source code or the database (dependency direction, forbidden imports, singletons, schema, secrets). ## 2026-09-02 — R-008's root cause found: there was never an unexplained mode, only a misread stack line

**Context:** `main` had been red on `apps/api/membership-revoke.integration.spec.ts`'s two-concurrent-owners test across four CI occurrences since 2026-08-26. `PHASE_1_DEBT_CLOSURE.md` D-6 had already spent **165 local reproduction attempts** (150 isolated-scenario loops, 15 full local suite runs) and returned zero anomalies, refuting the deadlock hypothesis outright (`pg_stat_database.deadlocks` delta of 0; no 5xx in any occurrence). Three investigations had left the root cause `UNDETERMINED`. The record described **two** failure modes: an explained guard-timing `403` (occurrence 4 only) and an unexplained one in which `successes` read empty **despite the server log showing a clean 200** for the test's own uniquely-identified organization — a contradiction the record stated openly and could not resolve.

That contradiction was the whole difficulty, and it was an artifact.

**Options considered:** the session's instruction proposed three lines of attack — an environmental differential between the local machine and CI, a hypothesis that the client lost a response the server really sent, and the `fileParallelism: false` + `pg_stat_activity` experiment R-008 had named and never run. A fourth was available and was tried first because it was cheapest: **re-read the primary evidence rather than the summary of it.** The archived CI logs were still within retention, and nobody had gone back to them since the record's own occurrence-4 addendum discovered that the AssertionError message is ambiguous between the test's two assertions.

**Decision:**

**Root cause: DETERMINED. All four occurrences are the same, already-explained mode. The "unexplained" one never existed.**

The archived logs for all four runs were retrieved (`gh run view <id> --log-failed`, and `--attempt 1` for occurrences 2 and 3, whose reruns had otherwise replaced the failing attempt) and the **Vitest stack frame** read instead of the message. Every frame points at `expect(losses)`; **not one points at `expect(successes)`**:

| Occurrence | Run | Commit | Frame | Line at that commit |
|---|---|---|---|---|
| 1 | `32987662296` | `09a8017` | `:452:20` | `expect(losses).toHaveLength(1);` |
| 2 | `33080832110` | `cfd13f3` | `:464:20` | `expect(losses).toHaveLength(1);` |
| 3 | `33081324846` | `46c03e3` | `:464:20` | `expect(losses).toHaveLength(1);` |
| 4 | `33555601029` | `55a5abf` | `:519:20` | `expect(losses).toHaveLength(1);` |

`git show <commit>:apps/api/membership-revoke.integration.spec.ts` confirms each line, with `expect(successes)` on the line immediately above. **The column is an independent confirmation:** `toHaveLength` begins at column **20** in `    expect(losses).toHaveLength(1);` and at column **23** in `    expect(successes).toHaveLength(1);`, and all four frames report column 20. Vitest's own code frame in occurrence 4 puts the caret under column 20 of line 519.

**So `successes` had length 1 in every occurrence — exactly one request returned 200, every single time — and `losses` was the empty one**, meaning the other request returned a status that is neither 409 nor 401. Occurrence 4's diagnostic dump names it: `statuses: [200, 403]`, `bodyBtoA: {"code":"FORBIDDEN","message":"No active membership in this organization."}`, final state `REVOKED`/`ACTIVE`. `SessionGuard` passes, then `OrganizationAccessGuard` re-reads a membership the winning request has just committed as `REVOKED`, and the loser gets `403` rather than the `409`/`401` the `losses` filter accepts. **R-007's actual invariant — exactly one success, the organization never reaches zero owners — held in all four.**

**How the error was made, which matters more than the error.** R-008's own occurrence-4 addendum had already established that both assertions emit the byte-identical `expected [] to have a length of 1 but got +0`, because both compare an empty array to a length of 1 and Vitest's default message names no variable. Having established it, nobody re-checked occurrences 1–3 against it. The original reading cited "line 451" where the log said 452, and every later investigation inherited that one-line error instead of re-deriving it. **It also explains D-6's 165 clean attempts completely: they were hunting a world in which neither request returned 200, and no such world ever occurred.** D-6's inference that its local repro "directly confirmed ... which only occurs when NEITHER status equals 200" is withdrawn on the same ground — the message it reproduced is ambiguous, so reproducing it confirmed nothing about which assertion CI hit. **D-6 stays CLOSED and its section is untouched**; what is withdrawn is one inference recorded in R-008, not D-6's own closure.

**The environmental differential was computed anyway, and it independently refutes F-3.** Two tooling scripts were added — `tools/diagnostics/environment-report.ts` and `tools/diagnostics/pg-activity-sample.ts` — and run against the full local suite. **This is the first measurement this repository has ever taken of how close the suite comes to `max_connections`**, a setting that previously appeared nowhere in the repository at all.

- Local: 8 cores → **7 Vitest workers** (`max(availableParallelism - 1, 1)`, `createForksPool`, vitest 2.1.9, non-watch). PostgreSQL 17.5, `max_connections` **100**, `superuser_reserved_connections` 3 → **97 usable**.
- Measured peak across a full green suite: **23 connections** including the sampler's own — **~24% of usable, 74 spare**. Peak `active` 3, peak `idle in transaction` 3. Wait events seen: `Client:ClientRead`, `IO:WalWrite`, `Lock:transactionid` — the last being exactly the row-lock contention `lockActiveForUpdate` exists to produce.
- `platform/db/pool.ts` passes no `max`, so each pool is `pg`'s default 10; each `createTestApp()` builds an `AppModule` carrying both `APP_DB` and `AUDIT_DB`. The naive ceiling (7 × 3 pools × 10 = 210) is nowhere near the measured 23, because `pg` pools are lazy and each spec file's real concurrent demand is 1–3 connections.
- **CI, now measured rather than inferred** (run `33630818221`, green, carrying the two new diagnostic steps): `availableParallelism` **4** -> **3** workers; PostgreSQL **17.11** (`postgres:17-alpine`); `max_connections` **100** with 3 reserved, **identical to local** - the alpine image does not lower it, which had been an assumption; **measured peak 10 connections (~10% of usable)**, peak `active` 3, peak `idle in transaction` 3. **CI peaks at less than half the local peak.** F-3 required CI to be closer to saturation than local; it is measurably further from it, on both axes. ## 2026-09-02 — R-008 investigated properly: deadlock hypothesis REFUTED, root cause remains UNDETERMINED, not fixed

**Context:** `PHASE_1_DEBT_CLOSURE.md` D-6. R-008's test failed a third time during the D-4 slice, on a commit that changed zero production code — three occurrences total, none explained. `RISK_REGISTER.md` R-008 named `ORDER BY id` on `lockActiveForUpdate` as a candidate fix; the explicit trap this entry avoids is applying it and declaring victory because the flake didn't recur — that would prove nothing, since "fixed" and "didn't happen this time" are indistinguishable without a reproduction to test against.

**Step 1 — evidence already available, read in full for all three occurrences (CI runs `32987662296`, `33080832110` attempt 1, `33081324846` attempt 1):**

All three fail at the identical assertion (`expect(successes).toHaveLength(1)`, line 451 at the time) with the identical message, byte-for-byte: `AssertionError: expected [] to have a length of 1 but got +0`. **This message is unambiguous about one fact**, confirmed by deliberately reproducing the exact message locally with a throwaway test (`statuses = [403, 403]` → `successes = []` → identical `"expected [] to have a length of 1 but got +0"`): `successes.length` was genuinely `0` in every occurrence, meaning **neither** `resAtoB.status` nor `resBtoA.status` equaled the number `200`. This is stated as fact, not inference, because it is exactly what causes this exact message and no other status-length combination does.

Each occurrence's structured request log was searched for the failing test's own organization id specifically (each test run creates a fresh, randomly-suffixed org that appears nowhere else in a 800-1200 line log) — occurrence 1's org (`dcaf22c7-...`) and occurrence 3's org (`d29a26b8-...`) each appear in the log **exactly twice**, both as `revoke` calls, confirming both log lines belong to this test's own two concurrent requests and nothing else. **What those log lines show, taken at face value, is a `200` and a `403`** for each occurrence — which is arithmetically inconsistent with the test's own confirmed `successes.length === 0`, since a genuine `200` would make `successes.length` at least `1`. **This contradiction between the structured request log (one clean 200) and the test's own JavaScript computation (no 200 at all) is the real finding of this investigation, and it is not resolved.** Either the request log's `200` does not mean what it appears to mean under whatever produced these specific failures, or something about how `resAtoB.status`/`resBtoA.status` were read diverges from what the server actually sent — no evidence gathered here distinguishes between those explanations. Stated as an open contradiction, not papered over with the more comfortable of the two readings.

**What all three occurrences have in common:** identical assertion, identical message, no 5xx status anywhere in either request of any occurrence, no server-side exception log near any of the three (checked directly — the one `HttpExceptionFilter` "Unmapped HttpException status 418" / "undefined" log line near occurrence 1 was already identified in `RISK_REGISTER.md` R-008's own prior correction as belonging to `error-contract.integration.spec.ts`'s unrelated deliberate-leak test, timestamped ~16 seconds later; re-confirmed absent near occurrences 2 and 3 as well). **What differs:** nothing conclusive — the durations (34ms/51ms/66ms) and org ids vary as expected across independent runs, but no pattern beyond "the same assertion fails the same way" emerges from three data points. **165 total executions of this exact race, zero reproductions.** This is reported plainly rather than downplayed: it means the trigger condition, whatever it is, either does not exist on this machine's environment (Windows, native PostgreSQL 17, different CPU/IO scheduling than an Ubuntu GitHub Actions runner) or requires a load/timing condition neither a tight loop nor 15 sequential full-suite runs produced. No failure state was ever captured locally, so step 2's "capture the full failure state including final `memberships` rows" could not be performed — there was nothing to capture.

**Step 3 — the deadlock hypothesis, tested directly rather than inferred:**

**Verdict: the deadlock hypothesis is REFUTED by this evidence, not merely left unconfirmed.** `RISK_REGISTER.md` R-008 previously called it "structurally plausible... stated explicitly as a hypothesis, not a diagnosis" — that hedge was correct discipline at the time, and this step is what that discipline was for: the hypothesis was tested, and it does not hold up. ## 2026-09-01 — Closing Phase 1 debt D-4: ESLint + typescript-eslint + Prettier, not Biome

**Context:** `06_IMPLEMENTATION_PLAN.md` Phase 0 item 2 requires both a linter and a formatter in the toolchain inventory — `PHASE_1_DEBT_CLOSURE.md` D-4, the last unmet Phase 0 deliverable, unbuilt since Phase 0 itself and never caught by any of the three Phase 1 gate reviews (all three audited Phase 1's own exit criteria, never Phase 0's checklist).

**Options considered:**
  A. Biome — a single Rust binary covering both linting and formatting, near-instant, minimal config, one dependency instead of several.
  B. ESLint + `typescript-eslint` + Prettier — the incumbent, heavier setup: more devDependencies, slower than Biome at any codebase size, but `typescript-eslint` can run **type-aware** rules (rules that consult the actual TypeScript type checker, not just syntax) where Biome's linter is syntax-only and cannot.

**Decision: B.** The type-aware distinction is the deciding factor, not a generic preference — argued from this codebase's own history, not from linter benchmarks in the abstract. `tsconfig.json` is `strict` with `noUncheckedIndexedAccess`, meaning this project already leans on the type checker for correctness beyond what most codebases ask of it; type-aware lint rules (`@typescript-eslint/no-floating-promises`, `no-misused-promises`, `no-unnecessary-condition`, `require-await`, `no-confusing-void-expression`) target exactly the class of bug an async, Promise-heavy, Kysely-and-NestJS codebase like this one actually produces — every controller in this repository is `async`, every repository call returns a `Promise`, and a missed `await` on `recordAuditEventDurable` (or its replacement, `runCapabilityAttempt`) is precisely a `no-floating-promises` finding, not a syntax-level one Biome could catch. This is not a hypothetical class of bug for this specific codebase: `sessions.revoked_at`'s "silently un-updatable through Kysely" typing defect (found and fixed twice, independently, first for `sessions.revoked_at` then again for `memberships.updated_at` — `CLAUDE.md`'s own history) is exactly the shape of subtle async/type-interaction bug a type-aware linter exists to catch before it ships, not after an integration test happens to notice.

Biome's real advantages — speed, one dependency, less config surface — are weighed and don't outweigh this at this codebase's current size: `typescript-eslint`'s type-aware overhead scales with project size, and this project (a few dozen source files as of Phase 1's close) will run it in low single-digit seconds, nowhere near threatening ADR-030's "harness runs in under two minutes" standard this project already holds itself to for the conformance harness. The dependency-count argument, which correctly stopped a runtime dependency for `modules/money`/`modules/calendar` (`AGENTS.md` §4, "prefer zero new runtime dependencies if the standard library genuinely suffices"), applies with less force here: ESLint/Prettier are **devDependencies**, never shipped, never a runtime attack surface or a bundle-size cost — the reasoning that correctly kept `modules/calendar` dependency-free doesn't transfer to dev tooling with the same weight.

**Package choices:** `eslint` (flat config, `eslint.config.js` — ESLint 9+'s config format, matching this project's ESM-first conventions), `typescript-eslint` (the unified package bundling parser + plugin + type-aware configs, not the older split `@typescript-eslint/parser` + `@typescript-eslint/eslint-plugin` packages), `eslint-config-prettier` (turns off ESLint's own stylistic rules so Prettier is the only source of formatting opinions — no fighting between the two), `prettier`.

**Prettier config, decided rather than left at defaults:** `printWidth: 120` (Prettier's default 80 would have wrapped far more of this codebase's already-consistent, fairly verbose-identifier style than the code as written actually needed — checked directly: most existing files already matched Prettier's defaults byte-for-byte once CRLF/LF was accounted for, and 120 kept the genuine reformatting diff to 61 files instead of a much larger one); `semi`/`singleQuote`/`trailingComma`/`tabWidth` left at what the codebase already did (`true`/`false`/`"all"`/`2`) rather than picked independently, since the existing style already matched; `endOfLine: "lf"`, matching `.gitattributes`' existing `eol=lf` normalization exactly rather than leaving it to whatever a given checkout's `core.autocrlf` produces. `.prettierignore` excludes `*.md` **entirely**, not case by case: `06`'s own item 2 groups "linter, formatter" with the TypeScript/NestJS toolchain, not documentation, and this repository's dated records (`DECISION_LOG.md`, `RISK_REGISTER.md`, every `PHASE_1_GATE_*.md`) must never be rewritten — excluding the whole extension removes that risk structurally rather than trusting a maintained exception list to stay complete as new dated records are added.
